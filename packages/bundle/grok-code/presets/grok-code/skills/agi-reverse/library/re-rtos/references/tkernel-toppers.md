# T-Kernel and TOPPERS/ITRON: context legality and static configuration

<CORE RULE>
The central lesson of the TRON/ITRON line is:

```
The same service call is legal in some execution contexts and illegal in others
```

So when you see a call such as `act_tsk` / `sta_cyc` / a device read or write, **recover "which context it runs in" first, then talk about semantics** — recovering only the API name produces the wrong conclusion.

Second: this line **depends heavily on static configuration**. **A task/handler with no ordinary code cross-reference may have come from generated configuration**.
</CORE RULE>

## 1. T-Kernel: three execution contexts

| Context | Character |
|---|---|
| **Task portion** | Ordinary task execution |
| **Quasi-task portion** | Processing that runs **because a specific task requested it**: it can identify the requesting task, it can define task-state transitions, and **it may issue service calls that enter a wait state**; but it has its own processor operating mode and stack space (it is an extension of the OS) |
| **Task-independent portion** | Activated by **factors unrelated to task progress** (external interrupt handlers, time-event handlers): **there is no "currently requesting task"** — it must not call a service that enters a wait state, or that implicitly names the requesting task; **no dispatch occurs** (dispatch is deferred) |

**Which contexts a service call is legal in is stated explicitly by the specification**. For example, "wait for a device request to complete" is legal in the task portion and the quasi-task portion, and **illegal in the task-independent portion**.

**Device-driver model**:

- A device is registered with `tk_def_dev`, and the registration names a set of handlers: **openfn / closefn / execfn / waitfn / abortfn / eventfn**
- These functions are called by device management and **run as a quasi-task portion**; they **must be reentrant**, and **mutual exclusion of the calls is not guaranteed** — the driver does its own exclusion when it needs it
- The concrete running context, more finely: open/close is the quasi-task portion of the task that called open/close; **execfn is the quasi-task portion of the task that called "start read/write"; waitfn is the quasi-task portion of the task of the function that called "wait"**

**Asynchronous request model**:

```
tk_rea_dev / tk_wri_dev → execfn (only starts it, does not wait for completion, returns)
tk_wai_dev              → waitfn (waits for completion)
```

- Completion order **is not necessarily request order** (it depends on the driver), but **processing results must stay consistent with request order**
- `tk_wai_dev` **waits only for the requests that were already being processed at the moment of the call**; requests issued later are outside the wait
- After a timeout return **the request is still being processed** — you must call wait again; the return code and the error field in the request packet represent the error of "the wait itself" and the error of "the processing result" separately
- Abort semantics differ: for a single request, abort the current processing; for multiple requests, **abort only the wait (release the waiter), do not abort the processing**

## 2. TOPPERS: identify the family first, then talk about semantics

The third-generation TOPPERS kernels (the ITRON line) are **four different families**, specified separately:

| Family | Role |
|---|---|
| **ASP3** | Base kernel: **no protection, single core** |
| **HRP3** | ASP3 + **protection** (memory protection, time partitioning, object-access protection, extended service calls) |
| **FMP3** | ASP3 extended to **multiprocessor** |
| **HRMP3** | **Protection + multiprocessor** together (HRP3 extended to multicore, or FMP3 plus protection) |

- Ready-queue design follows: HRP3 has **one ready queue per protection domain**; FMP3 has **one per processor**; **HRMP3 combines both** (by protection domain + by processor), and builds a queue only on processors a domain actually uses, to save memory
- Target-hardware requirements (HRMP3): homogeneous multicore (roughly 2–8), **every processor needs privileged/unprivileged mode and an MMU/MPU**, and every processor can execute the same binary
- As with ASP3: **no dynamic memory management inside the kernel**; kernel objects are created statically (only a fixed-size memory pool is provided to the application)

**Context types (they decide service-call legality)**: task context, non-task context, ISR, cyclic handler, and alarm handler each have their own legality rules.

## 3. Shared analysis requirements

1. **Identify the family / specification first** (ASP3 or HRP3/FMP3/HRMP3; the T-Kernel version and specification) — protection and multicore semantics differ
2. **Recover the context type of each call** (task / quasi-task / task-independent; task / non-task / ISR / cyclic / alarm)
3. **A task/handler generated by static configuration can have no ordinary xref** — find the configuration and the generated result, rather than calling it dead code

## Decision tree

```
Given a T-Kernel / TOPPERS target
├─ Identify the specification family first
│    ├─ T-Kernel: confirm version and specification (device management, system-state chapters)
│    └─ TOPPERS: ASP3 / HRP3 / FMP3 / HRMP3 (protection and multicore semantics differ)
├─ Some service call is "illegal" or denied
│    ├─ Recover its context type (task / quasi-task / task-independent; ISR / cyclic / alarm)
│    └─ Check the specification's valid-context table, rather than guessing from the API name
├─ Device-driver related
│    ├─ Which context each of the six handlers runs in (quasi-task portion)
│    ├─ Must be reentrant, and mutual exclusion is not guaranteed
│    └─ Asynchronous requests: start and wait are separate; completion order may differ but results stay in order
├─ Behavior after timeout
│    └─ The request is still being processed; wait again; a wait error and a processing error are two different things
└─ You cannot find the creation point of a task/handler
     └─ Static configuration generated it; do not call it dead code
```

## Tools and verification

- Specification: which family / version the target belongs to (protection and multicore support)
- Context: the execution-context type of each call, and the legality the specification states
- Devices: the handler set registered by `tk_def_dev`, and the running context of each
- Configuration: static configuration and generated results (task / handler / object)
- Verification: you can state together "specification family + this call's context type + whether this object is statically configured or dynamically created"

## Pitfalls on this platform (summary)

- **Recovering the API name and not the context**: legality depends entirely on context type
- **Calling, from a task-independent portion, a service that waits or that implicitly names the requesting task**: the specification forbids it
- **Treating a quasi-task portion as an ordinary task**: it has its own processor mode and stack space
- **Assuming device-driver functions exclude each other automatically**: exclusion is not guaranteed; the driver must handle it, and the functions must be reentrant
- **Inferring completion order from request order**: completion order may differ, but results must stay consistent with order
- **Assuming a request was aborted after timeout**: processing is still going
- **Mixing up a wait error and a processing-result error**
- **Not separating the four TOPPERS families**: protection and multicore semantics differ; applying one family to another is wrong
- **Expecting dynamic memory management inside the kernel**: kernel objects on this line are created statically
- **Treating a statically configured task/handler as dead code**
