# Shellcode analysis

## When to use / when not to use

- Use: what is in hand is a "raw code blob" (no PE/ELF/Mach-O file header) — an exploit payload, a second-stage payload extracted from a document or a script, code a dropper wrote into memory
- Use: the payload decodes itself (an XOR/ROL decode loop, generated by an msfvenom-class encoder) — statically it looks like garbage, and it has to be restored before analysis
- Use: the behavior must be checked by "running it with no environment" (the architecture does not match / there is no host process / it should not be triggered inside a real process) — Unicorn emulation
- Use: answering "which APIs this code calls, and what it is trying to do" (API-hash resolution)
- Do not use: a complete program that has a file-format header (that is the [[re-binary-core]] domain)
- Do not use: only a first-look conclusion is needed (file/hash/entropy; that is [[re-triage]])
- Note: emulated execution is dynamic execution and happens inside the sandbox by default (the top rule in [[re-analyze/platform-tips]]). A pure static extract or decode may skip the sandbox, but a real execution check after the decoded product is written to disk must enter [[re-sandbox]]

## Tool setup

Verify every tool before use. Static decoding in this skill may skip the sandbox. Emulated execution happens inside the sandbox by default (the top rule in [[re-analyze/platform-tips]]).

### python3 — the runtime for decode and emulation scripts

- Linux: `apt install python3 python3-pip` / `dnf install python3 python3-pip` / `pacman -S python python-pip` (usually already present)
- macOS: `brew install python` (or shipped with the Xcode CLT). Windows: the python.org installer (check Add to PATH) or `choco install python`. The Linux build inside WSL
- Check: `python3 --version`

### unicorn — the emulation workhorse (pip, Python 3)

- All platforms: `pip install unicorn` (Python 3)
- Check: `python3 -c "import unicorn; print(unicorn.__version__)"`

### capstone — disassembly output (pip, Python 3)

- All platforms: `pip install capstone`
- Check: `python3 -c "import capstone; print(capstone.__version__)"`

### binwalk — scan an embedded blob out of a host file

- The install channel and the version shape (v2 legacy / the v3 main line) are in the tool setup of [[re-fw-extract]]. Confirm the major there before use
- Check: `binwalk --version`

### xxd — hex viewing / locating a feature

- Debian/Ubuntu: `apt install xxd` (a separate package on the new version; the old version is in vim-common). Fedora: `dnf install xxd` (a separate subpackage on F38+; the old version is vim-common). Arch: `pacman -S xxd`
- macOS: shipped (bundled with vim). Windows: not shipped — use WSL or PowerShell `Format-Hex`
- Check: `xxd -v`

### objdump (binutils) — a raw-binary disassembly scan

- Linux: `apt install binutils` / `dnf install binutils` / `pacman -S binutils` (preinstalled on most distros)
- macOS: shipped. Windows: use rizin or Ghidra instead
- Check: `objdump --version`

### A disassembler — pick by `RE_DECOMPILER` or the environment

- [[re-radare2]] (rizin; command line / low memory; Raw Binary support is good; preferred). [[re-ghidra]] (GUI; Import File → Raw Binary and pick the architecture)
- Install and check as in those skills' tool setup

### scdbg — optional (a shellcode debugger)

- Search GitHub `Nypreo/scdbg` releases and download (a Windows executable; on Linux it can run under Wine, or use the Unicorn plan instead)
- Check: `scdbg.exe -f blob.bin` prints disassembly and an emulation result

### msfvenom — optional (generate a comparison sample / an encoder-feature reference)

- Kali: preinstalled (`apt install metasploit-framework`). Fedora: add the Rapid7 RPM repo and then `dnf install metasploit-framework`. Arch: `pacman -S metasploit` (the extra repo, 6.x)
- Check: `msfvenom -l encoders | head -5` (msfvenom can be used on its own; it does not depend on msfconsole's PostgreSQL)
- Purpose: generate a sample with a known encoder (for example `x86/shikata_ga_nai`) and compare the decode-loop instruction shape

## Steps

Run in order. Archive sha256 + path of every product (the blob / the decode result / the emulation output) (the evidence-chain requirement of [[re-ioc]]).

1. **Extract the shellcode blob (three sources: a file, memory, traffic)**:
   ```sh
   # 文件内嵌: 从宿主文件里扫嵌入段
   binwalk sample.bin
   binwalk -e sample.bin                    # 按签名自动提取
   # 定长段提取（已知偏移）:
   dd if=sample.bin of=blob.bin bs=1 skip=<off> count=<len>
   # ELF .text 段导出（载荷伪装成代码段时）:
   objcopy --dump-section .text=blob.bin sample.elf
   # 内存: 沙箱内 gcore 转储后按特征找（见 [[re-memdump]]）
   # 流量: tshark 提取 pcap 中的载荷字节（见 [[re-netcap]]）
   tshark -r c2.pcap -Y 'http' -T fields -e http.file_data > payload.hex
   xxd -r -p payload.hex blob.bin
   ```
   - The extraction principle: confirm the boundary before extracting — extracting more is better than extracting less (the entry is inside the blob). When the boundary is uncertain, extend the range first by the span of a 0xEB short jump or the decode loop
   - What the three sources share: the payload was often "processed" by the host (encoded / cut into blocks / rearranged) — `file blob.bin` the extracted blob and judge the entropy. If it is garbage, assume a decode layer first (step 3)

2. **Locate the entry (a 0xEB short jump / a disassembly scan)**:
   ```sh
   xxd blob.bin | head -20                   # 头部特征
   # 入口候选: 首字节 0xEB（jmp short，跳到解码器）、0xE8（call，自定位取 EIP）
   objdump -D -b binary -m i386 blob.bin | head -40     # 32 位 x86 裸反汇编
   objdump -D -b binary -m i386:x86-64 blob.bin | head -40   # 64 位
   ```
   - Common entry patterns: ① an `EB xx` short jump (jumps to the decode loop, leaving decoder space in front of the entry) ② `E8 00 00 00 00` + `pop reg` (call/pop self-location, taking the current EIP) ③ the decode loop starts immediately
   - On the rizin side: `rizin -a x86 -b 32 blob.bin`, then `s <candidate-offset>` + `pd 20` and look section by section (see [[re-radare2]]). Ghidra imports as Raw Binary (x86:LE:32:default) and marks a function with `L` at the candidate entry
   - The location test: the entry should be a "self-location + a decode loop + a jump to the decoded code" structure. Only a meaningful disassembled instruction sequence counts as the entry. If it is all garbage, do the step 3 decode first and come back

3. **Analyze the decode loop (XOR/ROL self-decode)**:
   ```sh
   # 特征指令（反汇编中找）:
   #   XOR byte ptr [reg+disp], imm    单字节 XOR 解码
   #   ROL/ROR byte ptr [reg], imm     循环移位解码
   #   ADD/SUB byte ptr [reg], imm     加减常量解码
   #   LOOP / JECXZ                    循环控制（计数在 ECX/RCX）
   ```
   - A static recovery: extract the decode parameters from the disassembly (the key byte / the shift amount / the length / the start) → reproduce it in python:
     ```python
     data = bytearray(open('blob.bin','rb').read())
     key, start, length = 0x55, 0x00, len(data)   # 参数来自反汇编
     for i in range(start, start + length):
         data[i] ^= key
     open('decoded.bin','wb').write(data)
     ```
   - After the recovery, go back to step 2 and locate the entry again — the decoded blob is the payload to analyze (the encoder may have a second layer)
   - A comparison check: msfvenom generates a sample with an encoder such as `x86/xor_dynamic`. Compare the decode-loop instruction shape and confirm the identification did not drift (see pitfall 2)

4. **Emulated execution (Unicorn runs with no environment, and hooks syscalls)**:
   ```python
   from unicorn import *
   from unicorn.x86_const import *
   blob = open('blob.bin','rb').read()
   mu = Uc(UC_ARCH_X86, UC_MODE_32)          # 按步骤 2 确认的架构选模式
   CODE, STACK = 0x1000, 0x3000
   mu.mem_map(CODE, 0x1000); mu.mem_map(STACK, 0x1000)
   mu.mem_write(CODE, blob)
   mu.reg_write(UC_X86_REG_ESP, STACK + 0x800)     # 设栈（不设必崩）
   def hook_code(uc, addr, size, user):
       if addr in API_ADDRS:                  # 步骤 5 定位的 API 调用点
           uc.reg_write(UC_X86_REG_EIP, addr + size)  # 跳过 stub
           print("hit api", hex(addr))
   mu.hook_add(UC_HOOK_CODE, hook_code)
   try:
       mu.emu_start(CODE, 0x100000)           # until 给大上限，非法访问即终止
   except UcError as e:
       print("stop:", e)                      # 缺 API/越界 = 预期终止点
   open('decoded.bin','wb').write(mu.mem_read(CODE, len(blob)))   # 解码产物
   ```
   - Letting the decode loop "run itself" is faster and more accurate than a hand recovery (the fix for pitfall 3). `hook_mem_write` can record where the decoded product lands (see step 4 of [[re-emulation]])
   - Handling a syscall or an API: Unicorn has no OS — disassemble and list every call target first, hook a known API call site to return a fake value, and record the arguments (stub it; see step 5 and pitfall 4)

5. **The host interaction surface (API resolution: walking kernel32, a hash lookup)**:
   - The standard way Windows shellcode gets an API: PEB → PEB_LDR_DATA → walk the module list to kernel32.dll → look up the export table by a name hash (the shellcode equivalent of GetProcAddress)
   - Locate the API set statically: in the disassembly, find the "push a 4-byte constant; ...; call" pattern. The 4 bytes are the API-name hash. Brute-force common hash algorithms and compare:
     ```python
     def djb2(s):
         h = 5381
         for c in s:
             h = ((h << 5) + h + c) & 0xffffffff
         return h
     for name in ['LoadLibraryA','VirtualAlloc','VirtualProtect',
                  'WriteProcessMemory','CreateThread','WinExec']:
         print(name, hex(djb2(name.encode())))
     ```
   - Algorithm comparison: the Metasploit family (generated by msfvenom) defaults API hashes to ROR13 (not djb2) — when brute-forcing a comparison, compute both. A hit confirms the generator
   - Recover the calling convention: decide the bitness first — 32-bit has no single convention. A Win32 API is commonly `WINAPI` / `__stdcall` (the callee clears the stack, and the epilogue is `RET n`). The program's own default is `__cdecl`, a member function is `__thiscall` (only `/Gz` changes the default to `__stdcall`), and the decision uses symbol decoration / the caller's stack balance / ECX-EDX use. 64-bit uses the unified x64 ABI (the first four integer/pointer arguments are RCX/RDX/R8/R9 plus 32 bytes of shadow space, fastcall-class, not `__fastcall`) — that decides the argument register/stack order and where the return value is (pitfall 3)
   - The API set = the behavioral intent: VirtualAlloc/VirtualProtect + WriteProcessMemory → injection. CreateThread/CreateRemoteThread → execution. WinExec/CreateProcess → running a program — this maps directly onto the ATT&CK mapping in [[re-behavior]] (T1055 process injection and the rest)
   - An emulation stub: add the API call site to API_ADDRS in hook_code, return a fake value by function (for example VirtualAlloc returns the address of an already-mapped block of memory), and watch where control flow goes

## Cross-domain handoff

- [[re-binary-core]]: this skill is that gateway's payload branch — specialized analysis of a raw code blob with no file-format header. The decompiler base reuses [[re-radare2]] / [[re-ghidra]]
- [[re-emulation]]: the emulation framework and hook techniques (step 4 of this skill reuses steps 2-4 of that skill directly)
- [[re-radare2]]: Raw Binary disassembly and an entry scan ([[re-ghidra]] does the same; pick by `RE_DECOMPILER`)
- [[re-memdump]]: extract shellcode from process memory (a default dump first; after gcore, find the blob by features)
- [[re-malware]]: the payload layer of a malicious sample — the decoded payload of a loader or a fileless sample comes to this skill
- [[re-anti-analysis]]: a payload span pulled out of a packed or obfuscated sample (the unpacked product comes back to this skill)
- [[re-triage]]: the first look before extraction (file/entropy decides whether there is an encoding layer)
- Cites the top rule in [[re-analyze/platform-tips]] (the sandbox) and the "static first" principle (locate statically first; go dynamic only as needed)

## Pitfalls

- **Position-independent addresses (there is no base-address concept)**: symptom — jumps and data references in a Ghidra/objdump disassembly are all "garbage" addresses, and analyzing them as virtual addresses does not line up; cause — shellcode has no PE/ELF header and no fixed base. Position-independent code uses a relative offset and call/pop self-location. The offset, not an absolute address, is the truth; fix — analyze by the offset inside the blob (rizin `s <offset>`, and xrefs look at the relative offset). Import into Ghidra as Raw Binary and mark a function from the candidate entry. Do not line up absolute addresses
- **Encoder variants (msfvenom has several encodings)**: symptom — after the entry is located, the disassembly is all junk bytes, and no "normal code" is found; cause — the payload was generated by an encoder (shikata_ga_nai/xor_dynamic and the rest), and everything is ciphertext until the decode loop runs; fix — find the decode loop first (XOR/ROL signature instructions + LOOP), and use the step 4 emulation to let it decode itself, or generate a comparison sample of the same encoder with msfvenom and confirm the instruction shape. The key of shikata_ga_nai is inserted dynamically, so a static key-recovery method fails — emulation is the first choice
- **A host dependency (recover the calling convention first)**: symptom — emulation behaves oddly at some point, the stack is scrambled, or the return value is wrong; cause — shellcode is designed to run inside a host process, and it assumes the host is already initialized (loaded DLL bases, stack alignment, the calling convention); fix — decide the bitness and the calling convention before stubbing (on 32-bit, integer/pointer arguments are mostly on the stack, and the callee/caller stack cleanup decides; on 64-bit the first four integer/pointer arguments are in rcx/rdx/r8/r9). Initialize the stack page to approximate the host layout, and return a reasonable value from each API by its signature
- **Emulation is missing an API (a stub)**: symptom — when Unicorn reaches `call kernel32...` or `syscall` it stops with UcError, and control flow cannot continue; cause — Unicorn has no OS, so neither the kernel nor the DLLs exist; fix — step 5 resolves the API hash and recovers the real API set first, stubs by function (the hook at the call site returns a fake value and records the arguments), and when needed hook_mem fills in the memory map (the "new page" returned by VirtualAlloc is mem_map'd first)
