## 2026-09-01 · session retrospective

**JNIEnv table-slot location (hook plaintext / the registration table)**: symptom — you want JNI-layer string plaintext or the dynamic registration table, but do not know where to hook; cause — JNIEnv is a function-table pointer (`[env]` = the JNINativeInterface table), each API is a table slot (offset = slot number × 8), and the key slots are `NewStringUTF`=0x538 (slot 167) and `RegisterNatives`=0x6b8 (slot 215); fix — `memory.pointer([env]).getLong(0)` takes the table base, the slot value is the implementation address, and a code hook on that address sees x1=plaintext and LR=call site on a NewStringUTF hit; on a RegisterNatives hit, read the methods array (three pointers: name / signature / address). Static location of call sites: search the whole library for `ldr xN, [xN, #0x538]`. Source: Android commercial-app native-layer analysis practice

**Bare-call matching when the registration table is unavailable (rebuild the dynamically registered function table)**: symptom — dynamically registered native methods whose registration table (method name + signature + address) is stored encrypted, strings finds nothing, and they are not registered at runtime (the emulator has no ART); cause — the registration table itself is encrypted and registration depends on a real runtime; fix — bypass the registration table: (1) scan all of `.text` for function entries (`stp x29,x30` prologue) (2) leaf filter (no internal bl in the function body) (3) bare-call `callFunction(addr, jniEnv, 0)` (a fresh emulator per candidate so state does not leak) (4) match by return shape: 0/1=boolean, a small value=long/enum, a pointer=String/callback (5) cluster by global-read features (adrp target page) and group. Verified: 158 candidates, zero crashes; 14 boolean, 2 long, and 8 pointer functions confirmed. Source: Android commercial-app native-layer analysis practice

**Emulation boundary for lazy decrypt / delayed registration**: symptom — inside the emulator JNI_OnLoad runs the full path and the registration-slot hook gets zero hits, so you think logic was missed; cause — the commercial app delays string decryption / method registration until the Java call chain fires (first use of the class); the emulator cannot load dex classes, so the call chain cannot be constructed; fix — first verify statically that "the startup path really does not register" (execution-path tracing + slot hook), then judge it as runtime-triggered; the final capture of strings / the registration table goes to on-device frida; the emulator goes as far as it can, and you do not force it.
