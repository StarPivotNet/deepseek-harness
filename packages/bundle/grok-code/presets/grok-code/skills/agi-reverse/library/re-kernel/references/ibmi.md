# IBM i: single-level store / the MI layers / the program model / pointers and activation groups

<CORE RULE>
**Two facts decide everything**: everything is an **object**, and all storage sits in a **single address space**.

```
main storage and auxiliary storage are not distinguished → memory + disk = one 64-bit address space
an object is accessed by [name], not by a hardware address
```

Add the split between **two kinds of pointer** and **two storage models**, and an `object address` must never be treated as "a pointer currently backed by DRAM".

**Do not apply the POSIX file / process model** — every concept from that layer has a counterpart here, with different semantics.
</CORE RULE>

## 1. Layers: what sits on what

```
MI (Machine Interface)         ← programs and processes are [system objects] here; ILE support is implemented here
  ├─ timi (technology-independent interface)
  └─ PASE                      ← takes another road: the SLIC syscall interface directly, bypassing TIMI
SLIC / LIC (System Licensed Internal Code)  ← interrupt handling, exception routing, part of the runtime implementation
OS (ILE runtime / OPM support / the various services)
```

- **Call-flow tracking at the MI layer is by "procedure", not by "program"** — MI instructions have two kinds: an external program call, and a "call through a procedure pointer"
- A **process** on MI is a system object (Process Control Space); an **activation group is not a system object**; it is part of the MI process object
- **PASE does not go through TIMI**: it has a syscall interface to SLIC, so a call that crosses the PASE ↔ SLIC boundary has extra cost

**Reversing meaning**: given a piece of code, decide **which layer** it is on first — an MI-layer object, code generated by the ILE runtime, or an AIX-style binary inside PASE; the tools and the semantics differ for all three.

## 2. The program model: OPM / EPM / ILE

| Model | Traits |
|---|---|
| **OPM** | a program object is compiled directly from a source member; calls are **mostly resolved at runtime** (late binding); usually a single language; **modules, procedures, service programs, and binding directories are not supported**; **it must run in the default activation group** |
| **EPM** | a transitional form (the C/400 and Pascal era); still resolved at runtime |
| **ILE** | introduces modules, a binder, and an optimizing translator; supports mixing languages |

**ILE's three objects**:

| Object | Notes |
|---|---|
| **`*MODULE`** | output of an ILE compiler; contains one or more **procedures**; **cannot be executed directly**; bound into a `*PGM` / `*SRVPGM` |
| **`*PGM`** | binds one or more modules and names an **entry module**; **a single entry point**; **bind-by-copy** — procedures are resolved at compile time, the cost is small, but when the same module is bound into several programs there are several copies in memory |
| **`*SRVPGM`** | an executable unit with many entry points (one per procedure); **bind-by-reference** — the client stores a symbolic link, **resolved when the program is activated**; **there is no entry module** |

- **Signature and binder language**: a binder description file manages the **signatures and export list the service program supports** (exported symbols, program level, signature, level check); when a client program is activated, the bound service programs are activated too, and a **signature match** is done
- A **binding directory** stores where binding information comes from
- A module can also **export a data item**: the exporter allocates and initializes it, and other modules import and share that storage

**Reversing meaning**: a `*PGM` **contains** its modules; a `*SRVPGM` is **not embedded** in the caller, and is **loaded into memory on the first call** — "changing the service program does not require recompiling the caller" is the direct consequence of that difference.

## 3. activation group: the runtime boundary for storage and resources

An activation group is a **runtime working-storage container** allocated to run one or more programs. It provides:

```
PSSA (program static storage area, global static data)
PASA / the call-return stack (local variables)
heap storage (dynamic data)
```

- Each activation group has its own control information, so it can have **a different protection state, file use, and commitment control**
- **A job has two default activation groups**: the operating system uses one, the application uses one; **an OPM program must run in the default group**; an ILE program can too (but then it loses modules / procedures / service programs and similar features)
- Common choices:

| Choice | Semantics |
|---|---|
| **named** | the first program creates it, later programs "plug in"; it disappears **only when the job ends or it is reclaimed explicitly** |
| **`*NEW`** | system-named; created on the call and destroyed when the program ends; **a service program cannot use `*NEW`** |
| **`*CALLER`** | the same group as the caller; no new group (usually the recommended value for a service program) |
| **`*ENTMOD`** | the binder decides from the entry module |

- **The scope of an override and of an open file is also at this layer**: the scope can be the activation group, the call level, or the job; an override issued from the default group usually takes effect by call-stack level, and one issued from an ILE activation group takes effect for that group

**Reversing meaning**: "who this static variable belongs to, and why this file override did not take effect" is answered by the activation group, not by the program.

## 4. Two kinds of pointer and two storage models

| | **system pointer** | **space pointer** |
|---|---|---|
| Points at | an **object** (with type information) | an offset inside a space |
| Shape | 16-byte tagged | an address |
| What it can do | resolve an object, call, authority check | address bytes inside one space directly |

**Two storage models coexist**:

| | **single-level storage** | **teraspace** |
|---|---|---|
| Scope | global (any job that holds the pointer can access it) | **local to the job** (normally visible only to the job that owns it) |
| Composition | several 16 MB units | one contiguous address space, containing several independent allocation areas and unallocated gaps |
| Size | — | on the order of 100 TB |
| mmap | **not supported** | supported |
| Pointer | — | **8 bytes** |
| Sharing across jobs | pass the pointer | **only through a shared-memory API** (`shmat` / `mmap` and similar) |

- **teraspace is not a space object**: it is not a system object, **it cannot be referenced with a system pointer**, but a space pointer can address it inside the same job; **it exists only from job start to job end**
- An ILE program / service program can be built `*TERASPACE` / `*INHERIT` / `*SNGLVL`; **an OPM program can use only `*SNGLVL`**
- **`*INHERIT` adopts the storage model of the activation group it is in**, and requires `ACTGRP(*CALLER)`
- **A teraspace-model program cannot be activated into an activation group whose root program uses single-level storage** (including the OPM default group); `*TERASPACE` cannot be paired with the default group
- The heap follows the storage model by default; some languages can choose the heap separately (for example mapping `malloc` to the teraspace version)

**So reversing has to ask three questions**: is this pointer a system pointer or a space pointer? does this address belong to single-level storage or to teraspace? which storage model is this program / service program? (The third question decides the legal answers to the first two.)

## 5. Exceptions and pointer-use limits

- **space addressing violation**: an attempt to operate outside the current space, or a reference to an **unallocated page** inside teraspace
- The exception's **data carries**: the **system pointer** of the object associated with the space, the **space offset**, and the **space class** — the space class can distinguish primary / secondary associated space, implicit process space (automatic / static / activation-group heap / constant / handle heap), **teraspace**, and **teraspace used by PASE**
- **Limits on using a tagged (16-byte) pointer** (remember these for data flow and forensics):
  - A tagged space pointer into teraspace **can be used only by the process that owns that teraspace** — after it is inherited by a `fork` child, or stored into shared memory by another process, **treat it as unusable**
  - **It must not be stored into memory mapped from a byte-stream file** (the `mmap` / `shmat` class); even if it lives in a region created from a shared-memory object, **a process other than the holder cannot use it reliably**

## 6. The job / thread boundary

- **teraspace is born and dies with the job**; sharing across jobs must go through a shared-memory API
- Library resolution (for example a library-list search) is **per thread**
- The ILE runtime **may keep `errno` per activation group** — to judge the value, it must be read in "the same thread, the same activation group"
- **Not every system API is thread-safe** (the API reference marks them one by one); calling a non-thread-safe API through JNI produces unpredictable results

## 7. Identifying executable material (the first layer when you have an artifact)

| Means | Use |
|---|---|
| **DMPOBJ (Dump Object)** | dump object contents to a spool file; usable for a **diff of two `*PGM` / `*SRVPGM` objects** |
| **compile with DBGVIEW(`*LIST` / `*ALL`)** | **extract the compile listing** through the debug API; cheaper and more readable than a binary diff |
| object compression (`CPROBJ` / `DCPOBJ`) | a `*PGM` / `*SRVPGM` / `*MODULE` and similar **may be in a compressed state**; **when it is used, the system automatically supplies a decompressed version** — so "the file does not look like code" may only be the compressed state |
| version / timestamp | embedded structures such as compile time make two artifacts compiled almost at the same moment **never identical** — do not call that tampering |

**Note**: a `*MODULE` is usually created in a temporary library, and **is no longer needed once it has been bound into a program** — so not finding "that original module object" on the system is normal; the code is inside the `*PGM` / `*SRVPGM`.

## Decision tree

```
Got an IBM i target
├─ decide the layer first
│    ├─ an MI-layer object / an ILE runtime artifact / an AIX-style binary inside PASE
│    └─ the tools and the semantics differ for the three
├─ which object was obtained
│    ├─ *PGM (bind-by-copy, contains the modules) / *SRVPGM (bind-by-reference, many entries)
│    ├─ *MODULE (not directly executable; it may have been discarded after binding)
│    └─ compressed? decompress / inspect first; do not call it "not code"
├─ references and storage
│    ├─ a system pointer (points at an object) or a space pointer (an offset inside a space)?
│    ├─ single-level storage (global, sharing by passing a pointer) or teraspace (local to the job; cross-job needs a shared-memory API)?
│    └─ is the program's storage model (*TERASPACE / *INHERIT / *SNGLVL) compatible with the target activation group?
├─ static data / file-override behavior looks wrong
│    └─ check the activation group (PSSA / PASA / heap and override scope are all at this layer)
├─ an exception
│    ├─ space addressing violation → look at the system pointer / offset / space class in the exception data
│    └─ a tagged pointer used across fork / across processes → treat it as unusable
└─ comparing artifacts
     ├─ prefer the compile listing (DBGVIEW)
     └─ when diffing with DMPOBJ, exclude embedded differences such as library name / creation time / PTF level
```

## Tools and verification

- Layer and object: object type and the library it belongs to; MI-layer call flow (traced by procedure)
- Program structure: bound modules and the entry module, export / import symbols, the service-program signature and binder language
- Runtime boundary: the activation group's storage areas (PSSA / PASA / heap) and override scope
- Pointers and storage: the distinction between a system pointer and a space pointer; which of teraspace and single-level storage it belongs to
- Verification: be able to state together "which layer this object is on and what it is + which kind of pointer it has and which storage it points into + which activation group it runs in"

## Pitfalls on this platform

- **Treating an object address as a pointer backed by DRAM**: memory and disk are one address space
- **Understanding storage as disk number / cylinder / sector**: the physical disk is hidden by LIC
- **Applying the POSIX file / process model**: here it is objects + qualified names + system pointers
- **Assuming a library is only a directory**: a library is itself an object, a container object
- **Mixing up the two kinds of pointer**: a system pointer points at an object; a space pointer points at an offset inside a space
- **Mixing up the two storage models**: teraspace is local to the job and is not an object; across jobs it can be reached only through a shared-memory API
- **Storing a tagged teraspace pointer into shared memory, or letting a child process inherit it and keep using it**
- **Expecting to find "that original `*MODULE`" on the system**: after binding it is usually no longer needed
- **Calling a compressed object damaged / not code**: it is decompressed automatically when used
- **Calling a binary-diff result tampering**: embedded fields such as the compile timestamp necessarily differ; prefer the compile listing
- **Reading `errno` in the wrong activation group**: the runtime may keep it per group
- **Assuming an OPM program can enter any activation group or use `*TERASPACE`**: it cannot
- **Treating PASE and the native environment as the same call boundary**: PASE bypasses TIMI, and crossing the boundary has extra cost
