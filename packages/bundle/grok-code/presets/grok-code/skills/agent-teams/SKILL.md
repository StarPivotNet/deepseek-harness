# AgentTeams captain protocol (DSH Grok)

<SUBAGENT-STOP>
If you were dispatched as an AgentTeams member, ignore this skill. Follow your assigned task contract and report via `agent_teams_*` with the current attempt_id. Captain protocol is for the captain only.
</SUBAGENT-STOP>
Be fast, accurate, strong, and smart: use live catalog tools, dispatch Agents on 2+ independent domains, never invent tools/facts/file content, never claim without this-turn evidence. Proactive multi-agent is active in every mode. Start a team in this turn for multi-file edits, independent parallel implementation, durable handoff, or quality gates, or when parallel work would materially improve speed or quality. Do not start AgentTeams for one-file or this-turn-only work — edit those yourself. Do not wait for the user to say AgentTeams. Do not demote an edit onto a write-capable `subagent`. Before `agent_teams_create`, load session-cognition if needed, read this session's `$DSH_HOME/cognitions/<project>/<sessionId>/cognition.md` when it exists (project = last component of cwd, sessionId = current session id; never workspace `.dsh/cognition.md`, never another session's ledger), and fold live Goal / Constraints / Kills / Next / Queue into that file so members can read the same facts. Silent full-auto: every team uses approval="automatic" — create, roster, DAG and lead in this same turn, no Web plan, no user review step, never call agent_teams_approve. This holds for user-named AgentTeams / /agent-teams as well. Never use approval="required". Plan mode must not create a team that would edit until `exit_plan_mode` reports approved. AgentTeams members each take one role on an independent domain; the captain keeps the `todo_write` queue. On `@nanmicoder/dsh-agent-teams` 0.1.23, `memberMaxDepth` defaults to 0, so a member does not call `subagent` or `send_message` and executes the assigned edit itself. Every member and task contract must be complete, standalone: the member does not share this conversation, so include goal / scope (files) / constraints / inputs / output format / acceptance.

Follow this protocol:
1. Call agent_teams_create with a team name and the goal as description. `plan.members` does not accept `executionPrompt`. Put the contract in the task `description`. `executionPrompt` belongs on `agent_teams_add_member`.
   - All teams: approval="automatic". Members you add spawn immediately and the scheduler runs ready tasks. Do not wait for a Web plan, do not ask the user for confirmation, do not call agent_teams_approve.
   - Never use approval="required". Staged Web plans are off. Never call agent_teams_approve.
2. Call agent_teams_add_member once per role the goal needs (researcher, engineer, reviewer, ...). Members are durable continuable members immediately. By default a member snapshots your current provider/model/reasoning route; use a different route only when the goal or user requires it. Members that are not reviewers pass `reasoning_effort` as `off`, `low`, or `medium` — not `high` or `xhigh`. Reviewer members pass `off` or `low` — not `medium`, `high`, or `xhigh`. They are not production-code work. Prefer `off`. Do not overthink. The reviewer must emit tools only during the review (0 user-facing words) and speaks only in the final six-slot report. Omitting inherits the captain's effort. This desktop profile does not set `memberMaxDepth`, so it stays 0. Do not tell a member to call `subagent`. A profile that sets `memberMaxDepth` to 1 may allow one read-only `subagent`; that call still uses `set_subagent_reasoning_effort` at `off` or `low`, and it is never an edit.
3. Analyze the goal and create the smallest useful task DAG. Every agent_teams_create_task call must include a non-empty subject, including verification and review tasks. Independent work should be parallel; dependencies are only genuine prerequisites.
   - Automatic team (always): finish the roster and DAG in this turn, then lead. Do not end the turn to wait for plan review and do not ask the user anything before leading.
   - Never stage a Web plan and never call agent_teams_approve. If a plan must change, agent_teams_edit_plan the still-pending work and keep leading.
4. After an automatic create, the scheduler starts ready work — but a member whose status stays `idle/unspawned` (empty member id) never started: its spawn threw inside the scheduler and only a Host log line records why, so no tool result will explain it. After create, call agent_teams_status once and check every member id. If any id is empty: do NOT send_message to that member (it routes through the same failing spawn path and only returns `delivered via mailbox` while burning a task attempt). Instead either wait one turn for the scheduler, or agent_teams_reassign_task the ready task to captain/another spawned member and do the work yourself. A task that reached attempt 1 can never be edited by agent_teams_edit_plan (`has already started`); only reassign_task moves it.
5. If the user explicitly asks to pause a running member, its open attempt remains parked after interruption; after answering the user, send that same member guidance with agent_teams_send_message so it continues the same attempt. Do not interrupt members for an ordinary user question that did not request a pause. If work must change owner, restart from scratch, or be taken over, call agent_teams_reassign_task first. Prefer another idle member or a retry with the same member. Use assignee=captain only for one ready task that you will personally drive to a terminal status in this same turn; never start a second captain takeover while one is unfinished, and never end your turn with captain-owned work open. Reassignment revokes the old attempt and waits for that member to quiesce, preventing late results from overwriting the new attempt.
6. Tasks carry attempt_id capabilities. Members must use the current attempt_id for updates; stale-attempt errors mean ownership changed. Check status after progress notifications until every required task is terminal and every member is idle/ready; do not busy-poll or require reports from members with no assigned work.
7. If the user names a configured profile / template / fixed roster, pass that name as profile= to agent_teams_create. After a successful profile create, do not recreate the same members. Seed profiles provide their template tasks; captain-planning profiles provide only the roster and guardrails, so you must design their DAG immediately. Add repair or retry tasks when review/test fails, but never make a new task depend on a failed task. Do not send_message to start the next stage; the scheduler assigns ready work. Watch every required task until it is terminal before deleting the team. Never perform a real deployment without explicit user confirmation.
8. Quality kinds (requirements, implementation, verification, review, repair, integration) need a contract: non-empty objective and acceptance; implementation/repair also need inScope and verify. Review/requirements can complete only with verdict=pass; needs_revision/reject must fail with findings. The system then opens repair + next review that depend on the successful source, never the failed review. Do not approve your own implementation. create_task no longer silently resumes a halted team — call agent_teams_resume with a reason, or create_task({resume:true, resumeReason}).
9. When the user explicitly requests full quality-mode planning, use this order unless a constraint forbids a stage: requirements → implementation → verification → review → integration. Build that entire DAG immediately: an implementation may be created before requirements finishes when its dependency chain includes that requirements task. This is supported; do not wait for requirements to run and do not inspect plugin source to confirm it. An integration task may depend on review round 1. If that review later returns needs_revision, the system automatically rewires still-pending downstream dependencies to the generated repair + next-review gate, so keep integration in the original plan instead of omitting or manually recreating it. Derive inScope and verification commands from the actual workspace or explicit profile; never assume src/ or pnpm test. Give every quality task a contract. Review acceptance must judge the latest implementation, not whether the gate rejects needs_revision. Do not write smoke-test scripts into tasks. Do not ask reviewers to submit needs_revision on purpose. Do not claim implementation or review yourself unless the user asked the captain to take over. After a failed review, wait for the automatic repair + next review. Do not recreate that loop by hand. halted means the human stopped the team; call agent_teams_resume before creating more work. escalated means the automatic review loop hit its ceiling; that is not halt.
10. Present the team's results to the user, then agent_teams_delete the team automatically. Do not ask whether to keep it; stopping a team aborts the Captain's current turn as well as member work, so only delete once every required task is terminal.

Tools: agent_teams_create, agent_teams_edit_plan, agent_teams_add_member, agent_teams_remove_member, agent_teams_create_task, agent_teams_reassign_task, agent_teams_claim_task, agent_teams_update_task, agent_teams_send_message, agent_teams_status, agent_teams_resume, agent_teams_delete. Do not call agent_teams_approve.

## This install

- The desktop profile has `@nanmicoder/dsh-agent-teams` 0.1.23. `memberMaxDepth` still defaults to 0. The profile `cordis.patch.yml` and the plugin patch leave it unset.
- 0.1.23 drops a deny-list name the host does not register and retries the member start. The 0.1.18 failure (the deny list always names `subagent`, spawn throws `unknown global tool`, the member stays `idle/unspawned`) is not the current bug.
- An empty member id whose task is already ready is still a failed spawn. Read the host log. Do not add a `memberMaxDepth: 1` pin to work around that old error.

## Don't

- Start AgentTeams for one-file or this-turn-only work — edit those yourself.
- Use `approval="required"` or call `agent_teams_approve`.
- Demote an assigned edit onto a nested write-capable `subagent`.
- Send `send_message` to a member whose id is still empty (`idle/unspawned`).

## Red flags (skill-specific; general excuses: see `using-superpowers`)

- "Subagents are faster for this multi-file edit" → that is AgentTeams; do not demote.
- "Wait for the Web plan" → automatic; lead in this turn.
- "Member said success" → you run the proof this turn.
