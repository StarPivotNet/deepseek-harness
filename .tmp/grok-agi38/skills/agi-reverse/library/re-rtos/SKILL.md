# RTOS structure analysis (FreeRTOS / ThreadX / Zephyr / RT-Thread / VxWorks / QNX / RTEMS / INTEGRITY)

<CORE RULE>
**The difference between RTOSes is not just "swap the TCB layout". It is "which address space the driver / service lives in, and when it gets registered".**

The kernels take different shapes (a linked-list task table / a compile-time device graph / a global symbol environment / a user-mode server / build-time configuration), but they share one thing: **the registration model decides what you can see** — a function with "no direct cross-reference" can mean, on different RTOSes, "normal (linker registration)", "normal (symbol resolution at load)", "normal (a user-mode server)", or "really unreferenced".

So the order is always: **first identify this RTOS's execution and registration model, then talk about tasks and kernel objects.**
</CORE RULE>

## Execution-model differences (not synonyms)

| Platform | Where the "driver / service" lives | Registration and discovery | What to decide first |
|---|---|---|---|
| FreeRTOS / ThreadX / RT-Thread | Same image as the kernel; tasks + a kernel-object table | Explicit create APIs + static object instances | The task table / TCB (this main document) |
| **Zephyr** | Same image as the kernel, but **the device graph is generated at compile time** | devicetree + Kconfig + **iterable sections**, `SYS_INIT` | Whether it is linker registration ([[zephyr]]) |
| **VxWorks** | **Two kinds**: DKM kernel mode / RTP user mode | DKM dynamic load + **a global symbol environment**; RTP uses standard ELF / `.so` | Separate DKM from RTP first ([[vxworks]]) |
| **QNX** | **A user-mode server**; a network driver is a shared object inside io-pkt | **Pathname registration** + message passing | Classify the form first ([[qnx]]) |
| **RTEMS** | Kernel and application share **one address space** | Build-time configuration (`confdefs.h`) + a device-driver table + a runtime linker | Configuration and the driver table ([[rtems]]) |
| **INTEGRITY / ARINC 653 / VxWorks 653 / PikeOS** | **Partitions** (space + time + resource, three domains) | Static configuration; partition-level **major frame / partition window** + intra-partition scheduling | **Align the partition window and the partition mode first** ([[partitioned-rtos]]) |
| **NuttX** | Same image as the kernel, or separated, **depending on the build** | Decided by the build model: FLAT is a direct call / PROTECTED goes through a syscall proxy / KERNEL goes through the MMU | **Classify FLAT / PROTECTED / KERNEL first** ([[nuttx]]) |
| **eCos** | Same image as the kernel; interrupt handling has three layers | ISR → DSR → thread, and each layer's synchronization differs | Decide which layer the work lands on ([[ecos]]) |
| **ThreadX Modules** | A resident kernel + dynamically loadable modules | **module preamble + a request ID through software dispatch** | Recognize the module ABI first ([[threadx-modules]]) |
| **FreeRTOS (context)** | Same image as the kernel; interrupt context is special | Task APIs and FromISR APIs are separate | Classify the context first ([[freertos-context]]) |
| **µC/OS, SYS/BIOS** | Same image as the kernel; **interrupts participate in scheduling** | The ISR explicitly notifies the kernel (enter / exit); layered threads Hwi > Swi > Task | Count interrupt enter/exit into schedule timing ([[ucos-sysbios]]) |
| **SAFERTOS, CMSIS-RTX5** | Same image as the kernel; **with access control and safety classes** | Per-task regions / protection domains, API and object access policy, an ISR deferred queue | First decide "who may access what" ([[safertos-rtx5]]) |
| **T-Kernel, TOPPERS** | Same image as the kernel; **whether a service call is legal depends on context** | Static configuration generates tasks/handlers; a device driver partly runs as a quasi-task | Recover the context type and the specification family first ([[tkernel-toppers]]) |
| **OSE / OSEck** | Same image as the kernel, but **messages can cross nodes** | Message-style IPC + a distributed transparent transport layer (shared memory / DMA / interconnect) | First decide whether the message peer is local ([[ose-oseck]]) |
| **Nucleus** | Same image as the kernel; **MMU/MPU subsystem isolation + a flat memory map** | Dynamically reload / restart / update applications and kernel modules (no need to stop the machine) | "A module was replaced but the system keeps running" and "isolation exists but VAs do not look per-process independent" are both not anomalies |

## Failure-mode decision table (the main entry of this skill)

**When "the call relationship cannot be found", "this code looks dead", or "the module will not load", suspect from this table first, then rule things out**:

| Symptom | Suspect first | Direction |
|---|---|---|
| Some init / device object **has no direct xref** | The registration mechanism: iterable section / `SYS_INIT` / `DEVICE_DEFINE` (Zephyr) | Decide it in the linker section and the map file; **do not mark it dead code** ([[zephyr]]) |
| A whole run of **regularly arranged** function pointers or structures | The same: a linker-generated registry | Understand it as a registry first, then consider a vtable / jump table / obfuscation ([[zephyr]]) |
| Early init does not call kernel services | Services are not yet available in the `PRE_KERNEL_*` stages (by design) | Do not call it "stripped"; conversely, a thread / mutex / sleep should first raise suspicion that the stage was classified wrong ([[zephyr]]) |
| A process **controls hardware with no kernel module** | A QNX user-mode resource manager | Find `resmgr_attach` / `dispatch_*` / `MsgReceive` and the registered pathname ([[qnx]]) |
| A network driver **is neither a process nor a module** | A `devnp-*.so` loaded by io-pkt | Find the io-pkt that loads it, and confirm native vs an old driver through the shim ([[qnx]]) |
| A thread priority **suddenly changes** in a sample | QNX message-driven **priority inheritance** / server boost | It is not an explicit `pthread_setschedparam` ([[qnx]]) |
| A thread **blocks in IPC for a long time** | `MsgSend` is synchronous wait by design (a normal state) | Find "who is supposed to reply"; a pulse is the non-blocking class ([[qnx]]) |
| A standalone module has **many unresolved symbols** | A VxWorks DKM links against **the target image's global symbol environment** | Locate the image and the VSB/VIP configuration first; do not call it malformed ([[vxworks]]) |
| A module does not work on the **same version** of VxWorks | The concrete image configuration differs | Check VSB/VIP, not the version string ([[vxworks]]) |
| `dlopen()` **does not behave like a Unix dynamic library** | The RTEMS runtime linker | It relocates into the current address space; an object name can be `libfoo.a:bar.o` ([[rtems]]) |
| The device callback's `file_operations` cannot be found | The RTEMS device-driver table (major = table index) | Recover `rtems_driver_address_table` and `rtems_io_register_name` ([[rtems]]) |
| The task count / scheduler **has no runtime creation point** | RTEMS build-time configuration generation | Find the translation unit that defines `CONFIGURE_INIT` ([[rtems]]) |
| A high-priority thread **does not run** (a partitioned system) | **Partition-level scheduling**: there is currently no execution window / budget for its partition, or the partition has not entered NORMAL | Align the major frame and the partition window first, then look at thread priority ([[partitioned-rtos]]) |
| "A, B, and C were written in a row and only C was read" | The overwrite semantics of a **sampling port** | That is an anomaly only for a queuing port ([[partitioned-rtos]]) |
| A function table at a fixed address was treated as obfuscation | An ABI of the APEX service-table class | Check it as a service table first ([[partitioned-rtos]]) |
| The same API decompiles completely differently across samples | NuttX **FLAT/PROTECTED/KERNEL** build differences | Classify the build model first; a very short API + an immediate trap is an auto-generated syscall proxy ([[nuttx]]) |
| Some address is "accessible to the user / a user fault" | They may come from **malloc and kmalloc** respectively (dual heap) | Separate the user heap from the kernel heap ([[nuttx]]) |
| The place that actually operates the hardware cannot be found | NuttX **upper half / lower half** layering | The hardware implementation is often in `arch/` or `boards/`, not in `drivers/` ([[nuttx]]) |
| A task-variant API was called from an ISR | The context classification or the symbol identification is wrong (FreeRTOS) | Classify task/ISR context and the API variant first ([[freertos-context]]) |
| Some address is "sometimes accessible, sometimes not" | An **MPU-restricted task**, or MPU regions were changed at runtime (FreeRTOS-MPU) | Check the region configuration and the runtime region-change calls ([[freertos-context]]) |
| An ISR only clears a status bit and returns | eCos's **DSR** does the real work | Check whether the ISR return value schedules a DSR ([[ecos]]) |
| Many "fill in a request ID → jump to a common dispatcher" | The ThreadX Module ABI | Build a request ID → service name map; do not call it obfuscation ([[threadx-modules]]) |
| The code address is outside the module memory area | An **XIP** module (instructions in Flash, data in RAM) | Do not call it control-flow hijacking ([[threadx-modules]]) |
| A switch happens at the end of an ISR / a task is ready but does not switch | **Interrupt enter/exit participates in scheduling** (µC/OS's enter/exit protocol; SYS/BIOS `Swi_disable` **also disables Task scheduling**) | Count interrupt enter/exit into schedule timing ([[ucos-sysbios]]) |
| The same address is accessible under one task and not under another | **Per-task MPU regions / protection domains** (SAFERTOS, RTX5) | Check the region configuration and the safety class; do not call it memory corruption ([[safertos-rtx5]]) |
| A handle does not look like a memory pointer | **An indirect object ID + a cross-reference table** (SAFERTOS ESM) | Do not expect to derive an object layout from it ([[safertos-rtx5]]) |
| An API called from an ISR did not take effect immediately | **The ISR FIFO deferred queue** (RTX5) | The object state changes only after the IRQ exits; that is normal ([[safertos-rtx5]]) |
| A service call is "illegal" or denied | **Context type** (T-Kernel task / quasi-task / task-independent; TOPPERS task / non-task / ISR / cyclic / alarm) | Check the specification's valid-context table; do not guess from the API name ([[tkernel-toppers]]) |
| The peer of a message / signal cannot be found | **A message can cross core / CPU / DSP / node** (OSE's distributed transparent transport layer) | Do not assume the peer is local, and do not look only at local syscalls ([[ose-oseck]]) |
| A module was replaced but the system keeps running | **Nucleus dynamic reload/update** (a flat memory map + MMU/MPU subsystem isolation) | See the execution-model table; do not call it a hijack first |

## When to use / when not to use

- Prerequisite: **first confirm which RTOS it is with characteristic strings / magic numbers / symbols** (this family is very easy to confuse with itself) → the RTOS section and the easily confused pairs of [[re-analyze/system-fingerprints]]
- Use: MCU/IoT firmware running an RTOS — locate the task table / TCB, split decompilation by task, recover kernel objects such as queues / semaphores / mutexes / timers
- Use: what you have is a raw image (no file system, no symbols), and you need to find the scheduler and every task entry from the startup-code chain
- Use: commercial RTOS firmware (VxWorks/QNX/RTEMS/INTEGRITY) — in-vehicle head units, avionics, industrial control; likewise start from the task / thread control block, and split the analysis by process / partition / task
- Use: the case where **"the driver / service does not exist as a kernel module"** or **"the registration relationship is not established in the source"** — first decide the execution model (user-mode server / global symbol environment / linker registration / build-time configuration); see the branches and the decision table
- Do not use: bare-metal firmware (no task table / scheduler; analyze it as an ordinary MCU image, [[re-fw-extract]] → [[re-binary-core]])
- Do not use: a Linux/Windows kernel (go to [[re-kernel]])
- Do not use: you only need to run it dynamically and watch behavior (go to [[re-fw-emulate]])

This skill is mainly pure static analysis (no sandbox; the top rule of [[re-analyze/platform-tips]]); when dynamic verification is needed, switch to [[re-fw-emulate]]. Tools are replaceable; the method is the core.

- Installation and version shape take the install matrix in the "Tool preparation" section of [[re-fw-extract]] as the single source of truth; this skill does not copy the package-name list

## Procedure

Execute in order, and archive each step's result (the task list, the kernel-object table, the Ghidra project).

1. **Prerequisite: image extraction and format identification (continues the [[re-fw-extract]] flow)**:
   - First finish [[re-fw-extract]]: binwalk unpack / dd split by offset / `file` + `readelf -h` to confirm architecture and endianness (big-endian ARM/MIPS firmware is common)
   - The product is usually a raw image (raw binary) or a single ELF; record the reset-handler entry and the RAM base (inferred from the linker script / startup code) — the task table and the TCBs are both in the RAM region, and are interpreted at link addresses
   - Confirm endianness and architecture before importing into Ghidra, so the whole analysis is not wasted

2. **RTOS identification: the startup-code chain + characteristic-string / symbol search**:
   - Startup-chain shape: reset handler → clock / peripheral / memory initialization → create tasks (`xTaskCreate` / `osThreadNew` / `tx_thread_create` / `k_thread_create` / `rt_thread_create` / VxWorks `taskSpawn` (commonly used in 6.x and earlier; it still exists in 7, and the internal implementation is taskCreate+taskActivate) or `taskCreate` (from 7 on; a created suspended task needs an explicit taskActivate) / QNX `ThreadCreate` / INTEGRITY ARINC 653 APEX `CREATE_PROCESS`) → scheduler start (`vTaskStartScheduler` / `osKernelStart` / `tx_kernel_enter` / `rt_system_scheduler_start` / VxWorks `kernelInit` / a QNX startup script brings up the system processes / INTEGRITY `START` enters the running state). Everything before the scheduler-start call site is initialization and belongs to no task
   - Characteristic strings: strings searches the kernel name ("FreeRTOS"), task names ("Idle" and similar), version / assert strings; when the ELF is not stripped, search symbols directly (`nm` / the Ghidra Symbol Table: `pxCurrentTCB`, `_tx_thread_created_list`, `_kernel`, `rt_thread_ready_priority_group`)
   - Commercial RTOS characteristic strings: VxWorks task names ("tIdle" the idle task (VxWorks 6.x+), "tRootTask" the root task) and version strings; QNX kernel / image names ("procnto", "imagefs") and system process names (resource managers conventionally named `io-*` / `devb-*` / `devc-*`); INTEGRITY partition / process names and ARINC 653 APEX service names
   - ThreadX has no version string to search; confirm it from the scheduler entry `tx_kernel_enter` + the TX_THREAD magic ID (step 3)
   - When the kernel is uncertain: find 3-4 task-create call sites and the call shape of the scheduler entry, and rule the kernels out one by one against each kernel's public structures

3. **Locate the task table** (pick the structure by kernel; after defining the structure in Ghidra, recover priority / state / stack pointer / task name field by field):
   - **FreeRTOS**: key fields of the TCB (tskTaskControlBlock) — pxTopOfStack (stack-top pointer), uxPriority (priority), pcTaskName (the task-name array, 16 bytes by default), pxStack (stack start; newer versions also have pxEndOfStack); the task lists are in static storage — pxReadyTasksLists[priority count] (an array of lists indexed by priority), xDelayedTaskList1/2, xSuspendedTaskList; the current-task pointer pxCurrentTCB. How to locate it: in the context-switch code, find reads and writes of TCB fields (save / restore the stack pointer, update the current-task pointer), and cross-reference back to static storage
   - **ThreadX**: the global doubly linked list `_tx_thread_created_list` (each TX_THREAD links through the created_next / created_previous fields), with the `_tx_thread_created_count` counter; key TX_THREAD fields — tx_thread_id (magic 0x54485244 'THRD', used to confirm the structure), tx_thread_name (task name), tx_thread_priority, tx_thread_state, tx_thread_stack_start/end/ptr (the stack region), tx_thread_entry (the entry function)
   - **Zephyr**: the global `_kernel` structure (struct _cpu in newer versions, struct _kernel in older versions) — current (the current-thread pointer), ready_q (the ready queue: a priority bitmap + a queue array indexed by priority), timeout_q (the timeout queue), the idle-thread pointer; there is also a global slist thread chain linking every k_thread; key k_thread fields — base.prio (priority), stack_info.start/size (the stack region), name (the thread name)
   - **RT-Thread**: rt_thread_ready_priority_group (the priority bitmap) + rt_thread_priority_table[RT_THREAD_PRIORITY_MAX] (an array of lists indexed by priority); key fields of the rt_thread structure — name, priority, stack_addr/stack_size, entry (the entry function)
   - **VxWorks**: key WIND_TCB fields — td_name (the task name, a string pointer into the string pool, not an inline array), td_sp (the saved stack pointer), td_priority (priority 0-255, 0 is highest), td_status, td_options, td_entry (the entry function), td_pStackBase/pStackLimit/pStackEnd (stack bottom / valid stack bound / actual stack bound), td_stackSize/td_stackHigh (stack size / historical high-water use). Watch the version difference: from VxWorks 7 on, WIND_TCB is an opaque type, taskLib.h provides only the VX_WIND_TCB_SIZE size macro, and field offsets change with version / SMP configuration. How to locate it: task-name strings live in the string pool (search "tIdle" / "tRootTask") and cross-reference back to the TCB that points at them; or infer field offsets from the context-switch code (save the register set to the stack, write td_sp, pick a task by td_priority), then walk the task list back to static storage
   - **QNX**: procnto (microkernel + process manager in one) manages thread control blocks — the thread is the scheduling unit, and a process is only an address-space container; key thread attributes — tid (the thread number inside the process), priority (256 levels, 0 is idle), the thread name (supported from 6.3.2+), the stack and the TLS region (containing tid/pid/stack base/errno) (the internal layout has no official public definition; attributes are observed through system-call parameters and the /proc side channel). How to locate it: QNX firmware is an IFS image (startup-header magic 0x00ff7eeb + the "imagefs" signature); use dumpifs to extract each system-process ELF and analyze them one by one (procnto is the kernel itself); on the application side, locate threads from kernel call sites such as `ThreadCreate` / `MsgSend`, and cross-reference thread-name strings back to the thread control block; in a live environment, DCMD_PROC_TIDSTATUS on /proc/<pid>/ctl can read thread state as a side channel
   - **INTEGRITY**: a partition is a space+time isolation unit — spatially each partition has its own memory region (enforced by the MMU), temporally execution windows are assigned cyclically by the module schedule (one round = a major frame); tasks inside a partition are ARINC 653 processes, and a process control block's attributes include the entry, stack size, base priority, and period / deadline. How to locate it: fully static configuration — allocated once at startup, no dynamic memory / no dynamic task creation, object addresses are fixed, and the boot table defines resource ownership; partition / process name strings are readable in the firmware and cross-reference back to the configuration table; call sites of ARINC 653 APEX service names (CREATE_PROCESS / SET_PRIORITY / GET_TIME and similar) are the kernel-service entries
   - Produce the task list: read the task name / priority / stack range / entry address from each TCB, one line per task

4. **Identify task stacks**:
   - Each task's TCB has stack-region fields: FreeRTOS pxStack/pxEndOfStack, ThreadX tx_thread_stack_start/end, Zephyr stack_info.start/size, RT-Thread stack_addr/stack_size, VxWorks td_pStackBase/pStackLimit/pStackEnd + td_stackSize (filled with 0xee by default; the VX_NO_STACK_FILL option turns that off), QNX thread stack bounds can be confirmed with help from the TLS region (stack base/tid/pid), and an INTEGRITY process stack is inside the partition memory region (the stack size is in the process-creation attributes)
   - Stack-region shape: a static array in .bss aligned by a configuration macro, or allocated from a memory pool; when FreeRTOS stack-overflow checking is on, the stack is filled with the 0xa5 pattern, which can help confirm the stack range
   - Split task boundaries by stack ownership: the stack range belongs to that task (locals, the nested call chain); when decompiling, use "which span of stack belongs to which task" to assign code; the stack-pointer value saved / restored at a task switch corresponds directly to the TCB's stack-top field

5. **Kernel objects (queues / semaphores / mutexes / timers)**:
   - Work backwards from kernel API call sites: `xQueueSend` / `xQueueReceive` / `xSemaphoreTake` / `xTimerCreate` (FreeRTOS), `tx_queue_send` / `tx_semaphore_get` / `tx_mutex_put` / `tx_timer_create` (ThreadX), `k_sem_take` / `k_mutex_lock` / `k_queue_get` / `k_timer_start` (Zephyr), `rt_sem_take` / `rt_mutex_take` / `rt_mq_recv` (RT-Thread) — the first argument of the call site is the object pointer; follow the cross-reference back to the object definition (a .bss static instance, or a memory pool)
   - Commercial RTOS kernel objects: VxWorks semaphores (semGive/semTake), message queues (msgQSend/msgQReceive), events (eventSend/eventReceive), watchdogs (wdCreate) — the call-site argument is the object ID; follow the cross-reference back to the static definition; QNX is a channel/connection model — a MsgReceive thread creates a channel, a MsgSend thread creates a connection, and a synchronous message puts the thread into the SEND/REPLY/RECEIVE blocked state (the message is copied straight across address spaces, with no intermediate buffer); a pulse is a non-blocking notification of 4 bytes of data + 1 byte of code; INTEGRITY inter-partition communication is a sampling port (overwrite-write semantics) / a queuing port (queue semantics), and inside a partition it is semaphores / events / buffers / blackboards, searched by ARINC 653 service name
   - A ThreadX object header has a magic ID that can confirm each one (take the official sources as authority; do not trust memory of secondary material): TX_QUEUE 0x51554555 'QUEU', TX_SEMAPHORE 0x53454D41 'SEMA', TX_MUTEX 0x4D555445 'MUTE', TX_TIMER 0x4154494D 'ATIM', TX_EVENT_FLAGS 0x4456444E 'DVDE', TX_BYTE_POOL 0x42595445 'BYTE', TX_BLOCK_POOL 0x424C4F43 'BLOC' (the TIMR/EVEN spellings in old material are not real; do not keep using them)
   - In FreeRTOS a semaphore / mutex is a special case of a queue (Queue_t) (the structures are isomorphic), and a timer is a Timer_t; after defining the structures in Ghidra, type propagation of call-site arguments improves the decompilation automatically
   - Infer an object's purpose from semantics: who sends and who receives, and what is processed after a take; that is the inter-task communication link

6. **Split decompilation by task**:
   - Analyze each task from its own entry: the entry argument of the task-create API → the function → rename it task_<priority>_<name>, and mark each task's entry in Ghidra
   - Blocking points inside a task (a delay / waiting on a semaphore / receiving from a queue / waiting for an event) are scheduling switch points; cut the task logic into state segments at the blocking points
   - Inter-task communication objects (queues / semaphores) connect different tasks: first draw a "task-object-task" graph, then dig into each one from the graph

## Platform branches (references)

The "driver / service model" of the following platforms differs enough from the generic task-table method to stand alone — **read the branch and decide the execution model first, then come back to this main document for task and object analysis**:

- [[qnx]] — **the user-mode server model**: a resource manager (`dispatch_create` → `resmgr_attach` → `dispatch_block/handler`, underneath which is `MsgReceive`), the distinction between the `connect` / I/O function tables and the `iofunc_*` default implementations, `devctl` and `_IO_DEVCTL`, **io-pkt and `devnp-*.so` (including the single-threaded stack context)**, message-driven **priority inheritance** and server boost, synchronous `MsgSend` blocking vs a pulse
- [[vxworks]] — **DKM (`.out`, kernel mode) vs RTP (`.vxe`, user mode)**, the link relationship between a DKM and **the global symbol environment**, the real cause of `undefined symbol` (the VIP does not contain the component), unresolved symbols in a standalone module are normal, VSB/VIP and "the same version, a different ABI environment"
- [[zephyr]] — **a compile-time device graph**: `DEVICE_DEFINE` / `DEVICE_DT_DEFINE` and linker sections, the level/prio of `SYS_INIT` and **the consequence of the return value**, **iterable sections** (a regularly arranged structure is not necessarily an obfuscation table), `/chosen` and `/aliases` are not hardware nodes, the map file decides membership, **LLEXT** (the export symbol table, pointers go invalid after `llext_unload`, User Mode needs `llext_add_domain`)
- [[rtems]] — **a single address space + build-time configuration**: uniqueness of `confdefs.h` and `CONFIGURE_INIT`, the six entries of `rtems_driver_address_table` and **major = table index**, `rtems_io_register_name`, **the runtime linker is not the Unix shared-library model** (`libfoo.a:bar.o`, lazy/immediate binding are equivalent, unresolved is not an error, a duplicate name is an error, the base image needs `rtems-syms`)
- [[partitioned-rtos]] — **partitioned systems (INTEGRITY / ARINC 653 / VxWorks 653 / PikeOS)**: two-level scheduling of **major frame + partition window** (three levels on PikeOS); partition modes IDLE/COLD_START/WARM_START/NORMAL (a process that "does not run" often has not entered NORMAL yet); the overwrite semantics of **sampling ports vs queuing ports**; INTEGRITY's fixed CPU/memory budgets and the static boot table; PikeOS's **fixed-address APEX service table** and the POSIX guest's system-thread mapping
- [[nuttx]] — **three builds, FLAT / PROTECTED / KERNEL**: the same API's artifact is completely different; PROTECTED's **auto-generated syscall proxy** (a very short function + an immediate trap, not a hook); **dual heaps** (user heap / kernel heap); the driver's **upper half / lower half** layering
- [[freertos-context]] — **ISR and task context**: the task variant vs the `...FromISR()` variant, `pxHigherPriorityTaskWoken` and `portYIELD_FROM_ISR` (the real switch happens after the interrupt exits), `configMAX_SYSCALL_INTERRUPT_PRIORITY` (a more urgent ISR must not call a single API, and the numeric direction of priority is reversed); **FreeRTOS-MPU** restricted tasks and runtime region changes
- [[threadx-modules]] — **the module preamble** (must be at the first address; the properties bits decide privilege / MPU) + **a request ID calls the resident Module Manager through software dispatch** (essentially a syscall table, not obfuscation) + XIP and copy-load
- [[ecos]] — **runtime**: the three layers ISR / DSR / thread, three sync levels and each one's lock (**an ISR cannot use a DSR-level lock; a DSR can signal a condition variable but cannot wait**), three driver models; **build time**: the CDL configuration system decides what is compiled in and the build target, the HAL vector table (VSR) and virtual vectors, the RedBoot startup order and **constructors run after vector-table initialization** (an overlapping region gets smashed), and where the debug stub goes
- [[ucos-sysbios]] — **interrupt enter/exit participates in scheduling**: µC/OS's paired `OSIntEnter` / `OSIntExit` protocol and "only the exit of the last nested ISR decides whether to switch"; SYS/BIOS **Hwi > Swi > Task** layering, **`Swi_disable()` also disables Task scheduling**, and Hwi/Swi share the ISR stack
- [[safertos-rtx5]] — **isolation features of a certified RTOS**: SAFERTOS ESM's **API access policy / object access policy / indirect object ID / per-task regions**; RTX5's **Safety Class / MPU protection domains / thread watchdog / object and SVC pointer checks**, and the **ISR FIFO deferred queue** (on overflow the system state is already inconsistent)
- [[tkernel-toppers]] — **context legality**: T-Kernel's three contexts, task / quasi-task / task-independent, and device drivers (the quasi-task portion, must be reentrant, mutual exclusion is not guaranteed); **the four TOPPERS families** (ASP3 / HRP3 / FMP3 / HRMP3) and static-configuration generation
- [[ose-oseck]] — **the signal model** (not a POSIX signal; **a signal number is not unique and must be paired with a secondary id**; register before send or it is lost; one event may be associated with several signals that must be drained) + **memory ownership of process / block / segment / pool** (allocation is only in **its own pool**; a cross-domain send is copied) + supervision and the error handler (including "what the end marker can detect, and what it cannot") + the difference between OSE and OSEck and **heterogeneous boundaries** (a signal crosses core/CPU/DSP/node; the system-information interface can show signal space and saved registers / stack)
- [[nucleus]] — **a flat memory map + protected regions + entitlement** (MMU on Cortex-A, MPU on Cortex-M; **not an independent VA per process**); **`NU_PARTITION_POOL` is a fixed-block memory pool** (a terminology trap that shares a name with an isolation domain); under `NU_SUSPEND` an empty pool suspends the task by design; **a module can be dynamically reloaded / restarted / updated without stopping the machine**

## Common pitfalls and traps

- **Analyzing code before the scheduler starts as a task**: symptom — the initialization sequence between the reset handler and scheduler start is treated as some task's main logic, and a long analysis never matches the business; cause — startup code (clock / peripherals / memory / creating tasks) runs before the scheduler, belongs to no task, and looks similar to a task entry's call shape; response — first locate the scheduler-start call site (vTaskStartScheduler/osKernelStart/tx_kernel_enter/rt_system_scheduler_start/kernelInit), treat everything before it as initialization, and always take a task entry from the entry argument of the create API
- **A stripped firmware has no task names**: symptom — the name field in the TCB is all empty / garbage / all zeros; cause — the firmware stripped symbols and cut the string table, so pcTaskName / tx_thread_name has nothing readable; response — distinguish tasks by stack-pointer range (each task has its own stack range), the priority value, and creation-order numbering; treat the task name only as an auxiliary clue
- **Linked-list vs static-table structure differences**: symptom — assuming a "static-array task table" finds no task list in the firmware; cause — each kernel organizes them differently: FreeRTOS is a static array of lists (pxReadyTasksLists indexed by priority) + the current pointer pxCurrentTCB, ThreadX is the global doubly linked list _tx_thread_created_list, Zephyr is an slist of every thread + the ready_q bitmap queues, RT-Thread is a priority bitmap + an array of lists, VxWorks tasks hang off a global task list (taskIdListGet has enumeration semantics), and QNX/INTEGRITY layouts are not public and are inferred from create / service call sites and handle tables; response — identify the kernel first and then pick the matching structure (step 3); do not apply one kernel's layout to another
- **A new RTOS with strings and symbols removed cannot be found by search**: symptom — strings and the symbol table have nothing, and kernel identification stalls; cause — a release firmware often strips symbols, turns off asserts / strings, and even cuts the version string; response — fall back on structural features: ThreadX magic IDs (THRD/QUEU/SEMA…), the FreeRTOS critical-section pattern (the fixed BASEPRI save/restore sequence on Cortex-M), the shape of the scheduler entry and the context-switch code, and compare TCB field offsets by version (infer the whole structure from how the task-entry argument is written into the TCB)
- **Treating the idle / low-priority fallback task as a business task**: symptom — an idle-loop task is dug into as the main business logic; cause — FreeRTOS automatically creates prvIdleTask (lowest priority 0), Zephyr has an idle thread, and VxWorks has a tIdle task; they only run hooks / cleanup / low-power code and are unrelated to the business; response — sort the task list by priority, rule out the lowest-priority infinite loop with no blocking as the fallback task first, and look for business tasks among high-priority tasks and tasks that contain blocking points (a queue / semaphore wait)
- **Treating context-switch / scheduler code as an ordinary business function**: symptom — a PendSV/SVC handler or the scheduler loop is traced as business logic, and the call relationships are a mess; cause — an RTOS context switch (save / restore the register set, switch pxCurrentTCB/current) lives in the same firmware as task code, and the decompiler treats it as an ordinary function; response — after recognizing the switch signature (save the full register set, update the current-task pointer, restore PC/LR from the stack top), mark it as scheduler code and do not go deep; look at task logic only in the call tree below the create-API entry
- **A commercial RTOS structure has no public definition, and old material's offsets cannot be applied**: symptom — applying a VxWorks 5.x WIND_TCB offset from the web to VxWorks 7 firmware produces garbage; cause — from VxWorks 7 on, WIND_TCB is an opaque type (taskLib.h gives only VX_WIND_TCB_SIZE), and the QNX thread control block and the INTEGRITY process-table layout are not public and change with version / SMP configuration; response — treat field names only as semantic clues, always infer offsets on site from the context-switch / create code, and verify them with the field read/write pattern
- **The task-name field is a string pointer, not an inline array**: symptom — looking for a fixed-length name array in the TCB the FreeRTOS way, and what you read is an address value; cause — VxWorks td_name is a char* into the string pool, and QNX/INTEGRITY thread names are the same; response — after taking the field, first decide whether it is an address or inline data (a cross-reference shows whether it points into the string region); after the firmware cuts strings the name field goes dead, so distinguish tasks by stack range / priority instead
- **QNX firmware is an IFS image and cannot be searched as a raw binary**: symptom — procnto or process code cannot be found anywhere in the whole firmware blob; cause — files inside a QNX image are often LZO-compressed, so strings and code are invisible; response — first locate the image by the startup header (0x00ff7eeb) + the "imagefs" signature, extract it with dumpifs (add -z when the startup-header fields were modified), and analyze the resulting per-process ELFs
- **INTEGRITY has no dynamic creation at runtime**: symptom — a partition-mode switch (COLD_START/WARM_START/NORMAL of SET_PARTITION_MODE) or a process start/stop (START/STOP) is analyzed as "create a task" logic; cause — INTEGRITY resources are allocated statically at startup, and runtime is mostly state transitions, with no dynamic memory allocation; response — creation-class code appears only on the initialization / configuration path; organize business logic by cyclic scheduling (the major frame) and APEX service calls
