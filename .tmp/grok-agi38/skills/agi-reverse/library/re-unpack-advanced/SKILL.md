# Unpacking: strong packers (VMProtect/Themida)

## When to use / when not to use

- Use: [[re-packer-id]] identifies a strong packer / virtualizing packer (VMProtect, Themida, Enigma, and similar); the simple-packer manual flow failed (it may be wrapped in a strong packer); the sample has layered anti-debug that blocks ordinary debugging
- Use: you need a clean sample for deep static analysis / a cracking prerequisite (the [[re-cracking]] path)
- Do not use: a simple compression packer ([[re-unpack-simple]] unpacks it quickly; do not use the heavy flow)
- Do not use: virtualized code where a black-box annotation is acceptable (mark-and-bypass saves about 10x the time versus restoration; see pitfall 2)
- Note: this skill is high cost and fails easily — first judge whether the target is worth it, and whether "annotate only, do not restore" is enough

## Tool setup

### Debugger (by OS)

- Debug a PE under Linux / Wine: [[re-gdb]] — `apt install gdb` / `dnf install gdb` / `pacman -S gdb`. **Wine direct read**: after `wine sample.exe`, `gdb -p <pid>` attaches (see the Linux branch of [[re-analyze/platform-tips]])
- Windows: [[re-x64dbg]] — official release zip. x64dbg's attach/breakpoint support is better on strong packers; prefer it for strong-packer scenes
- WSL: cannot attach a Windows process. Use Windows-side tools (WSL branch of [[re-analyze/platform-tips]])
- Verify: `gdb --version`; x64dbg can load the sample and single-step

### Scylla (IAT repair, including redirect handling)

- Built into recent x64dbg. Standalone: GitHub `NtQuery/Scylla` release
- Wine: the standalone Scylla can attach a Wine process (if it fails, finish in a Windows environment)
- Verify: Scylla appears in the x64dbg plugin menu

### scyllaHide (anti-anti-debug, GitHub)

- GitHub `x64dbg/ScyllaHide` release zip. Drop it in the x64dbg plugin directory and enable it. The release includes a Wine load method
- Role: hide debugger traces in bulk (NtQueryInformationProcess, ThreadHideFromDebugger, timing delta, debug port, and so on)
- Verify: ScyllaHide appears in the x64dbg plugin menu, and checking options hides the matching checks

### Script tools (unpack assist / annotation)

- idapython: ships with IDA ([[re-ida]] workflow). Verify: `File > Script Command` inside IDA can run Python
- rizin scripts: install matrix is in [[re-radare2]]. After install, verify with `rizin -v`

## Steps

Run in order. Record each step's result (evidence path + sha256; see [[re-triage]]).

1. **Anti-debug confrontation (scyllaHide approach)**:
   - Core check points: `NtQueryInformationProcess` (ProcessDebugPort / ProcessDebugFlags / ProcessDebugObjectHandle), `NtSetInformationThread` (ThreadHideFromDebugger), timing delta (`RDTSC` / `GetTickCount` / `QueryPerformanceCounter`), debug port (`NtQuerySystemInformation`), window / process-name enumeration.
   - x64dbg + ScyllaHide: check every option in the plugin menu → start the target in the hidden state. Under Wine, load with the wine method in the release, then attach.
   - **Attack the outermost layer first**: checks are usually chained. Statically locate the outermost check first (use [[re-ida]] / [[re-radare2]] to find the xref of `NtQueryInformationProcess`), hide the bulk with scyllaHide, and patch the remaining single points (see pitfall 1).

2. **Find the OEP (stack backtrace / memory-breakpoint combination)**:
   - **Entry ≠ the original program's logical entry**: a virtualizing packer still has an "entry" — after the EP loads, control flow enters packer code (Themida and similar enter the VM dispatcher). That entry is only the packer's load/dispatch point, not the original program's logical entry. "A virtualizing packer has no OEP concept" is inaccurate — the original entry still exists; it is only hidden inside / routed through the VM interpreter layer (see the pitfall "VM entry features mutate per build"). Locating it is this step's goal.
   - Stack backtrace: the tail of a strong-packer stub returns to the OEP with `ret` — single-step / breakpoint stops on `ret`, and the address at the top of the stack is an OEP lead (stubs are often multi-stage and multi-threaded; break several times and take the pattern).
   - Memory-breakpoint combination: `bp VirtualAlloc` (x64dbg; gdb/Wine uses `break *VirtualAlloc`) → after each return, check whether the allocated region was written with executable content → set a memory-access breakpoint on that region (View > Memory Map > target section > Set breakpoint on access) → break after the "last decrypt write". The OEP is nearby.
   - OEP features: a function prologue (`push ebp; mov ebp,esp`) plus dense normal API references. Record the OEP address and the image base.

3. **Dump (default dump first)**:
   - Linux/Wine: after running to the OEP, `gcore -o out <pid>` (default dump first; the full flow is in [[re-memdump]]. Before the dump, filter vsyscall/vdso from maps. Timing is in the key experience of [[re-analyze/platform-tips]]).
   - Windows: x64dbg to the OEP → Scylla → Attach → fill in the OEP → Dump.
   - Store sha256 before and after the dump, so you can compare.

4. **IAT repair (Scylla, including redirect handling)**:
   - `Plugins > Scylla > IAT Autosearch` → `Get Imports` → check "invalid" imports one by one.
   - **Redirect handling**: a strong packer hijacks API calls into a packer stub (a jump inside the VM) — for an invalid item that points at a VM stub: record the redirect (original API → stub address), and use an idapython / rizin script to annotate stubs back to the real API in bulk. Mark items that cannot be resolved and fill them by hand in later analysis (first `Get Imports` and confirm most normal APIs are already resolved).
   - **Recovering import relations when IAT Autosearch is abnormal (three leads)**: Autosearch finds nothing / many invalids. Do not only rerun Autosearch — (1) **API call chain**: locate the actual `CALL [addr]` call site and walk the address table backward; (2) **resolver function**: find the packer's API-resolve loop (the GetProcAddress call site, or its API-hash resolver), break on the **memory write point**, and record the address it writes into the IAT region; (3) a strong packer may use **API hash / dynamic resolve / direct syscall** (no IAT to repair) — switch to the "annotate" path (record call-site semantics; the idea is in step 5). **Tracing "the first API call" is not a general method**: a strong packer's resolve may happen on another thread / in a delayed stage, or go straight through a syscall (no API call to follow).
   - **Delay import / bound import / API resolver**: for delay imports, check Scylla's `Delayed` option (handles the delay-import table). For a bound import, judge by the bind timestamp and replace it with the real import. For an API-resolver packer (resolved only at runtime), run to the point where the API is actually used, then `Get Imports`. Do not Fix Dump in an early stage.
   - `Fix Dump` writes the repaired exe. Decompile again and verify the import table ([[re-ghidra]] / [[re-ida]]).

5. **Annotate virtualized code regions (if you do not restore, mark and bypass)**:
   - **Goal = lower the complexity of the VM interpreter layer**: the goal against virtualization protection is to lower the analysis complexity of the virtual-machine interpreter layer, not "restore a virtualized function to original code" — the latter has no feasible path for VMProtect/Themida. Two reachable goals: **VM restore** (a very small number of critical checks; restore handler semantics and rewrite the logic) or **annotate and bypass** (black-box observation of input and output). Accept the effort by "analyzability", not by "degree of restoration".
   - Locate the VM entry: VMProtect's VM_Entry shape is `push imm32; mov eax, imm; jmp vm_handler` (Themida is similar; section names `.vmp0`/`.vmp1`/`.themida`).
   - **Annotate rather than restore**: mark the virtualized function as a black box (record the entry address, argument count, and call-site list). Later analysis uses dynamic observation of input/output ([[re-gdb]] / [[re-x64dbg]] breaks at the VM entry and records arguments and the return value) instead of static restoration. Spend VM-bytecode reverse engineering only on the very few critical checks that truly need restoration (such as a registration-code check).
   - Product: a `vm_blackbox.txt` annotation list (address → note), archived with the analysis report.

## Pitfalls

- **Layered anti-debug chain → attack the outermost layer first**: symptom — scyllaHide fully on and you are still kicked, or passing one check is blocked by the next; cause — the checks are chained (the inner layer fires only after the outer one passes); fix — attack layer by layer: statically locate the outermost check first (xref `NtQueryInformationProcess` / the timing-delta function), hide the routine items in bulk with scyllaHide, patch the remaining single points, and continue
- **VM code restoration is expensive → mark rather than restore**: symptom — stuck for days in VMProtect bytecode reverse engineering, progress stalled; cause — the virtual-machine instruction set is private and the restoration effort is huge; **the goal was set wrong — original code is not a reachable product of virtualization protection**; fix — **goal = lower VM interpreter-layer complexity** (two paths: VM restore / annotate and bypass; see step 5). Mark the virtualized region as a black box, observe input and output dynamically (break the VM entry and record arguments/return value), and restore only the truly critical small piece (such as a registration-code check). **Accept by "analyzability", not by "degree of restoration"**
- **A multi-threaded packer (monitor thread) interferes**: symptom — kicked during debugging, the process self-destructs, or a breakpoint is rewritten by a thread as soon as it is set; cause — the packer starts a monitor thread that checks debugger state; fix — suspend the extra threads at the entry (x64dbg `Threads` panel Suspend; gdb `info threads` then continue a single thread), and advance only inside the target thread
- **The packer detects the debugger environment**: symptom — the process exits / self-destructs as soon as the debugger opens; cause — it checks the debug port, parent process name, window name (`FindWindowA`), and timing delta; fix — hide with ScyllaHide + rename the debugger process + statically patch the check point before attach. Still operate inside a sandbox snapshot ([[re-sandbox]])
- **Hardware breakpoints are detected by the packer**: symptom — the ESP-law hardware access breakpoint does not fire / the process exits as soon as it breaks; cause — newer Themida and similar detect the hardware debug registers (DR0-3); fix — hide with ScyllaHide's injection method (configure the matching `HookLibraryx86.dll` + `InjectorCLIx86.exe`), or switch to a memory breakpoint / TitanHide. If that still fails, statically patch the check point before attach
- **VM entry features mutate per build → do not rely only on a signature**: symptom — locating the VM entry / dispatcher by a tutorial's features fails, or the restored product is scrambled; cause — VMProtect's handlers mutate on every build (same opcode, different code), the dispatcher contains opaque predicates, and layered VMs (VM inside VM) stack (see opaque-predicate handling in [[re-deobfuscate]]); fix — try an automation framework first (x64Unpack hybrid emulation / DragonSlayer symbolic execution + taint tracking). By hand, record the handler execution sequence with a dynamic trace, and locate by "bytecode pointer register + loop dispatch" rather than a fixed signature
- **A sample named as a strong packer may not have virtualization enabled**: symptom — DIE reports VMProtect/Themida and you start the full strong-packer flow, but standard breakpoint technique would have unpacked it; cause — virtualization/anti-debug is a packer config option. Many real samples (RisePro/Amadey/PrivateLoader and similar) do not enable it and have no anti-debug; fix — try the ordinary flow first (VirtualAlloc breakpoint + memory breakpoint + single-step). Spend the high-cost restoration only after a VM dispatch-style entry is confirmed to exist
- **Treating the packer entry as the original entry / thinking a virtualizing packer "has no entry"**: symptom — you cannot find original logic at the packer entry (the VM dispatcher dispatch point), decide "a strong packer has no OEP concept", and give up, or you dig for original code inside the dispatcher; cause — confusing the "packer entry" (the load/dispatch point entered after the EP) with the "original program logical entry" (the original OEP hidden by virtualization); fix — the packer entry objectively exists (Themida enters the dispatcher as soon as it loads). Break on it / log it and watch init behavior. Locate the original logical entry per step 2, and handle the virtualized part per step 5
- **IAT repair stuck on Autosearch**: symptom — IAT Autosearch finds nothing / every import is invalid, and rerunning still produces nothing; cause — the strong packer rebuilds the import table at runtime (API hash / dynamic resolve / direct syscall), and there is no static table to search; fix — switch to the three leads in step 4 (call chain / resolver function / memory write point) to recover import relations. Items that cannot be recovered become annotations. "Trace the first API call" is not a general method on a strong packer (there is no call to follow under multi-thread / delayed resolve / direct syscall). Do not spend time on the first call
- **Treating "found the OEP" as a successful unpack**: symptom — you stopped at the OEP, dumped, and repaired the IAT, but the decompilation is still unusable (the code section is still packer data / relocations are scrambled / the exception table points at packer code / it crashes on run), and unpacking again does not help; cause — unpacking was narrowed to "find the OEP"; fix — **unpacking = restore an analyzable state**: the code section is real instructions, the import table resolves, and relocations / the exception table / the load config match the real image (check item by item; see [[re-format-pe]]). It is done only when verification passes. Repair whichever item is missing
- **Anti-debug already ran before the entry breakpoint (TLS callback runs first)**: symptom — you set a breakpoint / single-step at the EP, but the anti-debug check already fired (exit on start, or state was already changed). The entry breakpoint never took effect; cause — a TLS callback runs earlier than the Entry Point, and the packer hides anti-debug inside the TLS callback; fix — read the PE TLS directory first ([[re-format-pe]]), list the callback addresses, break at the callback entry / statically analyze the logic inside the callback. When an entry breakpoint did not catch the anti-debug, check TLS first (see anti-debug methodology AD18 in [[re-anti-analysis]])
- **Anti-debug does not exit; it feeds fake logic**: symptom — after the check point is passed the process does not exit, but it returns wrong data / algorithm results were changed / critical logic was skipped / execution was delayed, and the unpack product behaves strangely and is hard to locate; cause — anti-debug may deliberately manufacture fake logic (return wrong data / modify algorithm results / delay execution / skip critical logic), which is more common than an immediate exit; fix — after patching the check point, do not trust the output directly. Compare the result difference of the "check is true / check is false" paths. First confirm how the check result affects control flow (exit / reduced function / fake data / delay), then decide the change (see anti-debug methodology AD44 in [[re-anti-analysis]])
- **The packer detects a VM environment (VM-only channels)**: symptom — debugging / running the unpack flow inside a VM, the sample's behavior does not match expectation (a different init path, some functions do not fire, the unpack product is incomplete), but there is no anti-debug sign; cause — the sample calls VM-only channels such as the VMware backdoor / Guest Additions / vmtools to detect a virtualized environment — a high-probability virtualization-detection signal; fix — xref those call sites and the CPUID vendor leaf (0x40000000), confirm how the check result affects control flow, and if needed patch the return value to non-VM before the unpack flow (see anti-virtualization methodology AV-007 in [[re-anti-analysis]])
- **After a VM is detected it feeds fake logic / switches branches (not only exit)**: symptom — the sample does not exit in a VM, but the unpack product behaves strangely (fake data / skipped critical logic / a different payload), and behavior disagrees with the host; cause — the anti-virtualization check result affects the execution path, and the VM environment takes a different branch — anti-virtualization is not only for exiting; it can change sample behavior; fix — analyze the difference between the VM and non-VM branches. After patching the check point, compare the two paths' output before concluding. Do not trust the unpack product directly (see anti-virtualization methodology AV-008 in [[re-anti-analysis]])
- **IAT camouflage (allow-list API noise fill)**: symptom — after unpacking the import table "repairs normally" and decompilation is smooth, but the static conclusion does not match runtime behavior (none of the APIs in the import table is actually called); cause — malicious code/the packer injects allow-list API noise into the IAT (IAT camouflage; 2025 research confirmed it is used to mislead static detection), so the import table looks harmless; fix — xref and verify the actual `CALL [IAT]` call sites instead of trusting the import table. Compare real runtime calls with [[re-tracing]] / [[re-frida]]. Mark decorative imports separately, exclude them, then conclude
- **VMP 3.8+ obfuscation upgrade (instruction-text features stop working)**: symptom — analysis plugins that matched Handlers by instruction-text features before 3.8 all fail; cause — VMProtect 3.8 (reworked after the source leak) introduced five obfuscations: (1) full instruction mutation (almost every instruction except the XOR decrypt instruction has a variant, including several forms of pseudocode decrypt / read instructions / computing the Handler address); (2) memory-address constant encryption (any operand that contains a memory-address constant has that constant encrypted); (3) Handler mutation (the Handler that computes a virtual-register address is replaced); (4) Handler first-level fusion (adjacent Handlers merge, the "compute the next Handler address" block is dropped, and control jumps/connects directly); (5) Handler second-level fusion (for example the three Handlers "read addend → read augend → execute ADD" merge, virtual-stack operations are dropped, and bound registers do `add eax,ecx` directly); fix — change analysis plugins to semantic/data-flow matching instead of instruction text. When recognizing a fused Handler, note that virtual-stack operations may already have been replaced by a direct register link. Public 3.5.1 source ≠ 3.8+ can be copied (3.8 was reworked)
- **VMP 3.96 dump timing and true/false OEP**: symptom — dumping as soon as the VMP code section is dumped yields packer code, not the original program; cause — .text is mixed with VMP's own code, and a dump before decrypt/decompress finishes is garbage; fix — judge the decrypt stage with a **memory-attribute state machine**: ciphertext RX → (VMP grants write permission before writing plaintext) → writable during decrypt (WRITECOPY/RWX, the key signal) → back to RX when decrypt finishes (about to jmp OEP; that is the dump moment). VMP outer load flow: Loader bootstrap (compute delta, self-decrypt, walk the PEB for LoadLibrary/GetProcAddress) → environment check (anti-debug / anti-VT) → unpack the original image → fix relocations → rebuild the IAT (polymorphic stub) → initialize the VM engine → restore memory protection (**VMP restores with syscall 50; a kernel approach can break there**) → jmp OEP
- **VEH + Instrumentation Callback tug-of-war dump (ring-3 approach)**: symptom — VMP detects a debugger attach (syscall avoids the hook, detects a VM, detects test mode), and a kernel dump is complicated; cause — attaching a debugger is itself detected; fix — DLL injection + exception takeover, a fully brute-force way to avoid attach: make .text non-executable so DEP raises an execute violation → VEH takes over (accept only an execute violation with `ExceptionInformation[0]==8` and an address inside .text; at that moment **RIP is the real OEP**). Against a VMP scan: VMP repairs .text attributes and wipes the VEH callback → a watchdog thread reinstalls the callback on a timer (`NtSetInformationProcess` 0x28 ProcessInstrumentationCallback) + the Instrumentation Callback strips .text back to RW on every syscall return (a tug of war). Arming time uses LATE_ARM: **has been writable (decrypt happened) and is currently executable and not writable** (looking only at executable misreads the initial ciphertext state as the moment)
- **Treating a memory snapshot directly as a file (three requirements)**: symptom — dumped memory will not load in a decompiler (alignment / entry / section offsets are all wrong); cause — memory layout and file layout differ; fix — repair the PE after the dump: (1) change EntryPoint to the OEP; (2) FileAlignment = SectionAlignment (file alignment = memory alignment); (3) for each section PointerToRawData = VirtualAddress and SizeOfRawData = align(VirtualSize) (the raw offset equals the virtual offset directly; file byte X = memory RVA X). Then export the full dependent-module table to make IAT repair easier
