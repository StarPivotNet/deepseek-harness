# WinDbg dynamic debugging (Windows user mode + kernel)

## When to use / when not to use

- Use: Windows user-mode process debugging (launch/attach, breakpoints, single-step, registers); crash/exception analysis (`!analyze -v`); kernel debugging (two-machine/VM/local kd); driver and kernel-module analysis (together with [[re-kernel]]); crash dump (minidump/full dump) analysis
- Use: time-travel debugging (TTD) — `ttd.exe` records a .run trace and then replays it arbitrarily, suited to check/decrypt logic that you "reproduce once and inspect slowly" (see the TTD section of [[commands]])
- Do not use: a Linux target (use [[re-gdb]]); a macOS target ([[re-lldb]]); you only need lightweight GUI debugging ([[re-x64dbg]] is faster)
- Do not use: static analysis / decompilation only ([[re-ida]] / [[re-ghidra]] / [[re-binaryninja]]). A pure static flow that does not interact with the running state does not need a debugger
- Do not use: attaching a Windows process across the boundary from inside WSL (WSL branch of [[re-analyze/platform-tips]]: cross the boundary with Windows-side tools)

## Tool setup

Follow the Windows branch of [[re-analyze/platform-tips]] — attach needs administrator privilege. Debugging is dynamic execution and defaults to a sandbox (top rule in [[re-analyze/platform-tips]]).

### WinDbg (Microsoft Store build / Windows SDK / WDK)

- Store build (new-UI WinDbg): `winget install Microsoft.WinDbg` (or search "WinDbg" in the Microsoft Store)
- Classic build: in the Windows SDK installer, check "Debugging Tools for Windows"; `choco install windbg`
- WDK (includes the kernel debug tools kd.exe/kdnet.exe): `winget install Microsoft.WindowsWDK`, or check WDK in the Visual Studio installer
- Verify: open WinDbg, `File > Open Executable` loads any exe and stops at the initial breakpoint; `ver` in the command window prints the version
- Version difference: the Store build (WinDbg 1.x, Chromium UI) and the classic build (WinDbg 10.0.x) are command-compatible, but the UI and the attach flow differ. Dump analysis works in both (see [[gotchas]])

### Windows symbols (Windows SDK symbols / the public symbol server)

- Symbol path: `.sympath srv*C:\symbols*https://msdl.microsoft.com/download/symbols` (or set the environment variable `_NT_SYMBOL_PATH`)
- Kernel-module symbols: under kernel debugging, `.reload /f nt` (force a pull from the symbol server)
- Verify: `!analyze -v` output shows function names rather than a bare `+0x1a` offset

### Two-machine / virtual-machine kernel-debug environment

- Target machine (the one being debugged): `bcdedit /debug on` + `bcdedit /dbgsettings serial debugport:1 baudrate:115200` (serial) or `bcdedit /dbgsettings net hostip:<host IP> port:50000 key:<key generated by kdnet.exe>` (NET NIC, recommended on Windows 10+)
- VM scene: VMware/Hyper-V adds a serial device to the target VM (Named Pipe `\\.\pipe\com_1` / `-vmconnect`). Host WinDbg `File > Kernel Debug > COM` fills in the pipe name
- Local kernel debugging (test machine only, needs test signing): `bcdedit /set testsigning on`, reboot, then WinDbg `File > Kernel Debug > Local`
- Verify: after the target reboots it stops at "Waiting to reconnect" or enters the debug wait, the host WinDbg attaches successfully, `Ctrl+Break` after `g` can break in, and `lm` lists modules

### TTD (time-travel debugging, Windows 10 1903+)

- Record: `ttd.exe -out C:\traces target.exe` (or `-attach <pid>` to record an attach; `-monitor <process name>` watches launches)
- Open: WinDbg `File > Open` and select the `.run` trace file (or `Open Trace File`)
- Verify: `ttd.exe -help` produces output. After recording a stretch, open it in WinDbg, `!tt` can jump to any position, and `g-` can run backward (details in the TTD section of [[commands]])

## Steps

1. **Attach / launch a user-mode target**:
   - Launch: `File > Open Executable` selects the target exe and stops at the initial breakpoint (where ntdll has finished loading)
   - Attach: `File > Attach to Process` selects the target by PID/process name (**administrator privilege** is required to start WinDbg before it can attach a high-privilege process)
   - Command line: `windbg -p <pid>` / `windbg target.exe`. `-g` skips the initial breakpoint and runs

2. **Breakpoints / single-step / registers**:
   - Symbol breakpoint: `bp kernel32!CreateFileW`. Address breakpoint: `bp 0x401000`. `bl` lists, `bd`/`be` disable/enable, `bc *` clears
   - Symbols of a module that is not loaded yet use `bu` (unresolved; it binds automatically after the module loads) — `bu` is the right choice when the target DLL loads on demand
   - Command breakpoint: `bp address "r rax; k; gc"` — on hit it prints the scene and continues automatically, a log-style observation that does not interrupt the flow
   - Single-step: `g` continue, `p` step over, `t` step into, `gu` run until the current function returns
   - Registers: `r` all of them, `r rax` to view, `r eax=0` to modify (commonly used to bypass a check)
   - Memory/disassembly: `u 0x401000` disassembles, `dd`/`db` read memory, `dps rsp` shows stack contents
   - Search: `s -d 0x0 L?10000000 0xdeadbeef` (a value), `s -a 0x0 L?10000000 "text"` (an ASCII string) — used to find hard-coded constants/keys
   - Symbol search: `x module!*keyword*` (for example `x kernel32!*Virtual*`) — fuzzy match when the exact symbol name is uncertain

3. **Exception analysis `!analyze -v`**:
   - After the target crashes and stops: `!analyze -v` → read `EXCEPTION_CODE`, `FAULTING_IP`, `STACK_TEXT`, `PROCESS_NAME`
   - A kernel blue screen corresponds to a bugcheck code (`BUGCHECK_CODE`, for example 0xD1 a driver accessed invalid memory) — record the code before looking further. Common codes should be matchable to a fault direction
   - Scene recovery: take the `EXCEPTION_RECORD` address from `STACK_TEXT` and `.exr <addr>` (the exception record), then take the `CONTEXT` address and `.cxr <addr>` to restore the register scene, then `k` for the real call stack (the only reliable stack walk when the stack is damaged)
   - A dump scene is simpler: after opening the dump, `.ecxr` directly (automatically sets the register scene from the exception context) → `k` — the standard opening of minidump analysis
   - Dump analysis: `File > Open Crash Dump` opens a `.dmp` (user mode is generated with `.dump /ma`; a kernel blue screen uses `%SystemRoot%\Minidump\*.dmp` or a full dump). `!analyze -v` likewise produces the bugcheck code and the faulting module

4. **Kernel debugging (two-machine / VM / local kd)**:
   - Target-machine configuration is in "Tool setup". Reboot after configuring. The host `File > Kernel Debug` connects on the transport in use (COM/NET)
   - VM pipe serial flow: add a serial Named Pipe to the target VM → the target `bcdedit /dbgsettings serial` → the host `File > Kernel Debug > COM` fills in the pipe name (`\\.\pipe\com_1`) → reboot the target and wait for the connection
   - After connecting: `g` lets the target keep running. `Ctrl+Break` breaks back into the debugger at any time. `!process 0 0` confirms the session is alive
   - Local debugging: after `bcdedit /set testsigning on` and a reboot, `File > Kernel Debug > Local` (test machine only; this is not a way to use it on a production machine)

5. **Extension commands**:
   - `!process 0 0` (the full process list), `!process <EPROCESS> 1` (one process's details + threads). `.process /p <EPROCESS>` switches to the target process context, then `k`/`!thread`
   - `!teb` (the current thread's TEB), `!peb` (the current process's PEB — command line, loaded modules, environment block)
   - `lm` (module list; a trailing `(deferred)` = symbols not loaded, `(no symbols)` = no symbols), `lmv m <module>` (version + path), `lmi <module>` (image header)
   - `kv` (a full stack walk with symbols, commonly used in driver analysis). After `!analyze -v`, check `STACK_TEXT` frame by frame
   - Driver-specific: `lmv m driver-name` gets the base → `.reload /f driver-name` loads symbols → deep work hands off to [[re-kernel]]

6. **TTD replay (slow inspection of check/decrypt logic)**:
   ```
   ttd.exe -out C:\traces target.exe     # record
   WinDbg opens .run → g- / t- / p-      # run backward
   !tt 50                                 # jump to 50% of the trace
   !tt 7213:36                            # jump to a position (event index:step count)
   ```
   - Move the breakpoint forward/back: `!tt br` stops where a register value changes. `!tt bm` stops on a memory access
   - The first time a trace is opened, `!tt.index` builds the index (later opens skip it). A breakpoint `bp` also works during replay (it works on the trace)
   - Query API: `dx @$cursession.TTD.Calls("module!function")` counts calls/arguments (for example `...Calls("ntdll!mem*")`)
   - TTD limits: must run as administrator, user mode only, trace files are large (several GB), replay is read-only and cannot write memory (see [[gotchas]])

7. **Pseudo-registers and scripting (simple automation)**:
   - Pseudo-registers: `r $t0 = 0` starts a temporary variable. `$$ > <file>` redirects command output to a file (for example `$$ > c:\log.txt`)
   - Conditional execution: `.if (rax==0) { ... } .else { ... }` — pair with `gc` for logic inside a breakpoint
   - `!runaway` shows thread CPU time (find a busy-wait / infinite-loop thread). `!locks` checks lock state (hang investigation)

## Pitfalls

- **Symbols not configured → bare offsets and no function names**: symptom — `lm` ends with `(no symbols)`, and `k` prints `ntdll!+0x1a`; cause — the symbol path is empty or there is no `_NT_SYMBOL_PATH`; fix — `.sympath srv*C:\symbols*https://msdl.microsoft.com/download/symbols` then `.reload /f`. Kernel modules are the same (confirm the symbol server is reachable first)
- **Wrong kernel-debug configuration → the target blue-screens, waits forever, or will not connect**: symptom — after reboot the target stops in the debug wait, or it boots into the system without breaking; cause — the bcdedit transport type/port does not match the host, or local debugging on a single physical machine is limited (PatchGuard); fix — a VM serial pipe is the most stable (both sides use `\\.\pipe\com_1`). Recheck the configuration with `bcdedit /dbgsettings`. On a physical machine, prefer KDNET
- **32/64-bit command and register differences**: symptom — on a 64-bit target `r eax` changes the wrong value, and `!teb` fields do not line up; cause — an x64 context uses `rax/rbx...` (the low 32 bits are `eax` and similar), and a wow64 target's thread stack is at the x86 layer; fix — confirm the target bitness first. For wow64, `.load wow64exts` + `!wow64exts.sw` switches to the x86 context
- **When the stack is damaged, `k` is an illusion**: symptom — the call stack is garbage (addresses do not look like code); cause — the stack pointer was corrupted / memory was stomped, and an ordinary walk is not trustworthy; fix — use `.exr` to get the exception record, `.cxr` to restore CONTEXT, then `k`. When needed, take the scene directly from `STACK_TEXT` in `!analyze -v`
- **A blue-screen dump will not open**: symptom — `Open Crash Dump` reports a format error; cause — the minidump is incomplete (the disk was full), or a 32-bit WinDbg was used to read a 64-bit dump; fix — on the target, confirm the kernel pagefile is large enough (a crash dump needs a pagefile), and switch to a WinDbg of the same bitness
- **RPC calls share the entry NdrStubCall3 (reversing an svchost feature)**: symptom — you want to intercept/analyze some system feature (for example a Toast notification) and do not know which channel it uses to enter svchost; cause — the feature is implemented over RPC into the svchost process, and the entry is hard to find; fix — Process Monitor shows the target process loading rpcrt4.dll + RpcView confirms the RPC target process. **Every RPC server stub goes through rpcrt4's NdrStubCall3** (x64; NdrStubCall2 is the old x86, which ReactOS/Wine source can confirm) — break there and `kvn` to see the caller. Filter the target call: the third argument (r8) points at RPC_MESSAGE (+0x1C is the ProcNum method number, +0x28 is the interface-description pointer RpcInterfaceInformation → InterfaceId of RPC_SERVER_INTERFACE is at +0x04). **opnum is numbered by MIDL from 0 in method-declaration order** (for example PostNotification3 is at position 0x29 → opnum=0x29). In ObjectStublessClientN, rax=N is the ProcNum. Pitfall: NdrStubCall3 handles every RPC interface inside svchost. **Filter on both InterfaceId and ProcNum**, and intercept only the target method (intercepting the wrong one will hang other features such as Edge)
- TTD limits, version differences, and symbol-server details are in [[gotchas]]
