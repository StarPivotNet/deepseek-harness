## 2026-09-01 · session review

**Three forms of string protection (do not assume everything is encrypted)**: symptom — a strings scan of .rodata shows many printable strings but most "look garbled", and the verdict is that everything is encrypted; cause — commercial-app strings are stored mixed: a plaintext table (runtime class names / paths / debug strings) + a light transform (shifted storage / a first-byte marker, still in the printable range) + real encryption (a high-entropy block, runtime key); fix — layer statically first: (1) dump every .rodata string (2) classify by readability (1.0 = plaintext, 0.9+ = light transform, <0.5 = real encryption) (3) extract plaintext/transformed strings fully and statically, and for truly encrypted strings locate the runtime decrypt operation (movz/movk chain + eor) and decide whether the key is statically evaluable or generated at runtime. Source: Android commercial-app protection-system analysis, field work

**Error codes from environment checks point back at the check**: symptom — an init function returns a mysterious negative (something like -1005) and the check logic cannot be found; cause — the error code is often produced by a formula (`-1000 - errno`), and the source of errno is the check; fix — in the disassembly, find the error-code constant (movn/mov immediate) and walk the formula back to the upstream call: in this case `movn wN,#0x3ec` produces -1005, and the upstream `bl chdir(虚拟FS)` fails and returns errno. Bypass: hook the decision point (the branch condition), not the hooked function — hooking the function itself skips its side effects and later state goes missing. Source: Android commercial-app protection-system analysis, field work

**An emulator svc breakpoint is not a crash**: symptom — during a batch of bare calls in unidbg, "debugger break at: 0xfffe0xxx" is frequent and is misread as a crash and skipped; cause — unidbg implements JNI APIs as svc (the 0xfffe0xxx region). When they are called the debugger prints a breakpoint, and the function actually runs and returns normally; fix — distinguish: a breakpoint in the svc region = a JNI call (normal), Invalid memory fetch/read = a real crash; judge whether a function can run by whether the return value is produced, not by the breakpoint print. Source: Android commercial-app native-layer analysis, field work
